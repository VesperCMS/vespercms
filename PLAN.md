### 1. Tables in the writing view

**Seen.** Every table is a protected block, "Table, kept as written", edited as raw pipe text in a dialog or the source view. Changing one default in the integration's options table means editing pipe syntax by hand, escaping any `|`, and keeping the column count. Agency sites have the same tables (prices, opening hours, contacts), and raw pipe text is the most developer-like thing an editor meets in the studio. The playground has one table, in the accessibility fixture.

**Design.**
- **Reading, in core.** A table becomes a block of its own kind (`kind: 'table'`) with its syntax (pipe or Markdoc), its column alignment, and for each row and cell the exact range of the content, without pipes or padding. micromark's cell ranges are trimmed to that. For a pipe table in `.mdoc`, a row scanner splits each line at unescaped pipes. For `{% table %}`, a cell is its line after `* `. As with tags, the scanner's cells must agree with the parser's: the same number per row and the same inline content in each. When they disagree, the table stays as written.
- **Which tables become writable.** A table is writable only when every cell is one line of inline Markdown the writing view already writes back (text, emphasis, strong, code, links, images, strikethrough, and chips), and every row has as many cells as the header. These stay protected blocks, named as now:
  - HTML tables, and cells with inline HTML (`<br>` for a line break is common);
  - ragged rows, which GFM fills or truncates, so a grid can't show what the page shows;
  - footnote references, reference-style links, and links with titles;
  - `{% table %}` cells that hold blocks (lists, several paragraphs, fences) or carry annotations (`{% colspan=2 %}`, `{% align="right" %}`);
  - tables inside list items or quotes, which are already inside a protected block;
  - any table whose scanner and parser disagree.
- **Saving splices cells, not tables.** Each row and column gets an id when the body loads, so a move can be told from an edit. On save, core compares the table with how it loaded:
  - an unchanged row keeps its bytes, line ending included;
  - a changed cell rewrites only its content range, so one edit changes one line of a pipe table, or one `* ` line of a `{% table %}`;
  - a moved row moves its line as it is, a new row is written in the table's style, and a deleted row goes with its line ending;
  - a new, moved or deleted column changes each row (and the delimiter row) by exactly that cell, which it must;
  - an alignment change rewrites that column's cell in the delimiter row (`:---`, `---:`, `:---:`, `---`). A `{% table %}` aligns with annotations, which keep a table as written, so it isn't offered there.

  The result is re-parsed and must read back as the intended table, or the save is refused, as `editMarkdocTag` does. The writer lives in core (`editTable`, beside `editMarkdocTag`), so local mode, GitHub mode and the cloud splice with the same code, and the admin's `bodyItems` hands a changed table to it instead of the Markdown serializer.
- **Padding** (call T1). In a compact table a changed cell is written with its row's own spacing. In an aligned table the new text is padded to the column's width when it fits, so the row still lines up. When it's longer, it gets one space on each side, and that row's pipes stop lining up. GFM ignores padding, so the page is the same either way, and no other row changes. New rows follow the same rule, and rows written without outer pipes (`a | b`, valid GFM) keep that shape.
- **Escaping.** A `|` typed into a cell is written `\|`, inside code too, as GFM asks. A cell is one line: Enter in a cell never adds a line break.
- **The editor** (call T2). A writable table is one atom node, `vesperTable`, whose view is a grid: the WAI-ARIA data grid pattern with editable cells. Each cell shows its formatting and chips. Editing a cell opens the one-line Markdown editor in place (the `fields.markdown({ inline: true })` editor, with code from item 3). Committing a cell is one ProseMirror transaction, so Ctrl+Z undoes cell by cell along with the rest of the body.
- **Inserting** (call T4). "Table" in the toolbar's Insert menu and in the "/" list inserts a compact pipe table in every format: a header row and one row, two columns.
- The source view and the raw-text dialog still edit any table as text.

**Where it lives.** In the body, as a block, framed like a tag. It has a hairline frame, the header row on `surface-sunken` as the kit's Table has it, no zebra striping, and the focused cell's ring drawn inside the cell, as menu items draw theirs. A label line above it reads "Table · 3 columns", with one "…" button, "Table actions" (an overflow button, which §10.4 allows). Row and column actions hide behind it, and behind Shift+F10 on a cell. No new colour or panel. A table wider than the column scrolls inside its own container, as the entry list does at 320px.

**Keyboard and screen readers.**
- In the text, the arrow keys select the table as a block, announced as blocks are: "Table, 3 columns and 7 rows, selected. Press Enter to edit its cells." Alt+↑/↓ move it and Delete removes it, as for a tag's block.
- Enter moves focus into the grid, onto the cell last used (a roving tabindex). The arrow keys move by cell; Home and End go to the row's ends, and Ctrl+Home and Ctrl+End to the first and last cells.
- Enter or F2 edits the focused cell, with the caret at the end. In the cell, Enter or Escape stops editing and keeps the change; Tab and Shift+Tab edit the next or previous cell. Tab in the last cell adds a row, as word processors do, and announces it.
- Escape in the grid returns to the text with the table selected, as Escape inside a frame selects the frame. Shift+Tab from the grid reaches Table actions, as Tab from inside a frame reaches its Settings button; Tab leaves the table.
- Shift+F10 (or the menu key) opens Table actions for the focused cell:
  - insert a row above or below, or a column left or right;
  - move the row or the column (also Alt+↑/↓ and Alt+←/→ on a cell);
  - delete the row or the column;
  - align the column: left, centre, right, or as written (a radio group in the menu).

  The header row can't move below a body row or be deleted: a pipe table must have one.
- The grid has `role="grid"`, a name ("Table" with its column headers), `aria-rowcount` and `aria-colcount`. Header cells are `columnheader`, the others `gridcell`, and rows carry `aria-rowindex`. NVDA and JAWS switch to focus mode in a grid and read each cell with its column header. The cell's editor is named by its column and row ("Default, row 3").
- Changes are announced in the body's polite live region: "Row added below row 3.", "Column Default moved left.", "Row 4 deleted.", "Column Default aligned right."
- The accessibility rule for a table without a header row keeps working, on the file as written.

**Tests.**
- Core:
  - reading both syntaxes: alignment colons, escaped pipes, code spans holding pipes, compact and aligned tables, rows without outer pipes, CRLF;
  - every kind of edit changes only the bytes it must: one cell's range, one row's line, one column's cells;
  - a save is refused when its result would read back differently;
  - the scanner agrees with Markdoc and with micromark;
  - a snapshot like `tag-edits.md`: one cell edit per table in every test file.
- Corpus: vespercms.com's docs (Jeremy's own), the playground, and the committed four-site corpus, jazzy's 108 Markdoc files among it. Each table is either writable or kept with a reason. Editing each table's first cell changes only that cell, and opening and saving with no edit changes nothing. The count of tables kept as written is reported, to see what real content needs.
- Admin (jsdom): the grid's keys in both modes, Table actions, the announcements, and axe. `fidelity.test.ts` also types into every cell of every writable table.
- e2e (`studio`, keys only), on new playground fixtures: an aligned price table in Markdown, opening hours as a `{% table %}` (kept as written until it's built, under T3's (a)), a table inside a callout, and one kept as written. It edits a cell; adds, moves and deletes a row and a column; aligns a column; and tabs past the last cell. The file is checked byte for byte after each save. axe runs with the grid focused, a cell being edited, and the menu open.
- Docs: `content/markdoc-and-mdx.mdoc` says how tables are edited and which stay as written. CLAUDE.md gains a rule: change a table through `editTable`.

**Size.** Large, the largest item: about 15 commits, for core's reading and writing, the grid and its menu, fixtures, tests and docs. Fewer if `{% table %}` waits (call T3). No new dependency: the grid uses the kit's React Aria pieces and the compact editor.

**Risks.**
- Edge cases where a parser splits cells differently from the scanner, such as a backslash before an escaped pipe, or markdown-it (inside Markdoc) against micromark. The agree-or-keep rule leaves those tables protected, never wrong, and the corpus count shows how often it happens.
- Focus moving between the document, the grid and a cell's editor, inside ProseMirror. The chips' caret problems on a Mac (DECISIONS.md, "A chip is non-editable once") came from nested non-editable elements. The grid is one atom node whose view owns its focus, which keeps ProseMirror's caret walk out, but the e2e tests should cover the grid's edges on macOS too.
- An aligned table edited many times drifts out of line. That's the cost of the splice rule (call T1), and only one table in 48 is aligned.

**Free or paid.** Free, as the body editor is.

**Calls.**
- **T1. Padding when a cell changes in an aligned table.**
  - (a) Pad to the column's width when the text fits, else one space on each side, so only that row's line changes. Recommended: one edit changes one line, as the splice rule and "No unrelated diff" (DECISIONS.md) ask.
  - (b) Re-align the whole column. Tidy source, but changing one price rewrites every row in history, and "No unrelated diff" would need a dated exception.
  - (c) Never pad. The least code, but an aligned table goes ragged on its first edit, even when the text would have fit.
- **T2. How a table is edited.**
  - (a) A grid, as above. Recommended: the keys are predictable, and screen readers treat a grid as one thing.
  - (b) A table inside the text (`prosemirror-tables`, already part of `@tiptap/pm`), typed into like a word processor. Quicker to type across, but the arrow keys move through text rather than cells, screen readers' table commands are unreliable inside an editable region, and cell-by-cell splicing would have to map ProseMirror's own table model back to the source.
- **T3. Which tables come first.**
  - (a) Pipe tables first, and `{% table %}` when a site uses one. Recommended: every table in vespercms.com and the corpus is a pipe table, and none uses `{% table %}`. It stays a protected block meanwhile, and the design above already covers it.
  - (b) Both in one step. The grid and cell editor are shared, and `{% table %}`'s writer is small, but it adds a second syntax to test with no content to test it on.
- **T4. Inserting a new table** from Insert and "/". (a) Yes, a compact pipe table. Recommended. (b) Edit existing tables only.

### 2. History for an entry

**Seen.** Spec §7.4 says history "comes from git", and §10.3 puts it in the editor's "…" menu, but nothing shows who changed an entry or when, and nothing brings an earlier version back. On vespercms.com every docs change is a cloud publish, so its history exists only on GitHub, out of an editor's reach. PLAN.md's Phase 4 defaults said history waits for its own step after Phase 4.5.

**Design.**
- **Storage.** `StorageAdapter` gains two optional methods, present only where there's history:
  - `history(path, { cursor? })` returns a page of versions, newest first. Each has the commit, the path at that time (it differs across a move), the file's blob SHA, the time, who made it, the summary, and whether the studio made it (a `Vesper-Collection` trailer);
  - `readAt(path, commit)` returns that version's bytes.

  The memory adapter implements both, and `runStorageContract` tests them for every adapter that has them.
- **Who.** For a cloud publish the author is the app's bot, so the names come from its `Co-authored-by` trailers. Those are lists since 2026-10-21: the publisher first, then each draft's authors, with their IDs in `Vesper-Editor` in the same order. History comes after the cloud's half of that is live. In GitHub mode the editor is the author; in local mode, whoever made the commit. Names only, never email addresses. A change made outside the studio shows its author and "Changed outside the studio", with the first line of its message below in muted text.
- **Local mode** (`astro dev`). When the site's folder is inside a git repository, the dev API runs `git log --follow` and `git show` with `execFile` (no shell, the path after `--`), and only for files inside the site that a collection owns. When the working file differs from its last committed version, the list starts with "Saved on this computer, not yet in history". With no git, there's no History (call H2).
- **GitHub mode.** One GraphQL request per page of 20: the branch's `history(path:)`, with each commit's `file(path:)` for its blob (to be checked against GitHub's docs before building, as Phase 3 did). Bytes come by blob SHA through the existing IndexedDB cache, checked against the SHA. GitHub's history for a path doesn't follow a move, so at the commit that added the path, one REST call (`GET /commits/{sha}`) reads its files, and a `previous_filename` continues the history under the old path. The fake GitHub answers both from `git log` over its real repository.
- **The cloud.** A contract change in `@vesper/core` first (CLAUDE.md, "The cloud"):
  - `GET /sites/{site}/history?path=…&cursor=…` returns `{ versions: HistoryVersion[]; cursor?: string }`, with each version's commit, path, blob version, time, `by` (names, and member IDs from `Vesper-Editor`), summary, and whether the studio made it;
  - `GET /sites/{site}/history/{commit}?path=…` returns that version's bytes. The API resolves the blob from that commit's tree and refuses a path outside the site's folder (a monorepo's other code) or a commit not on the branch. `POST /blobs` keeps serving only the head's tree and drafts, so it isn't widened to any blob in the repository;
  - restoring needs no endpoint: it's an ordinary draft save, checked by `changeAccess` like any other.

  `runCloudContract` gains: two publishes list newest first, with their editors from the trailers; a moved page keeps its earlier versions; a version outside the site's folder is refused; viewers can read history. `CloudClient` and `scripts/cloud-fake.mjs` follow. The cloud's repository then runs history over the git proxy and caches each page by path and head commit in the site's Durable Object, since an older page never changes.
- **Entries, in `ContentService`.** `history(collection, id)` maps the entry to its file. For a `file()` collection, where entries share one file, it keeps only the versions in which this entry's own JSON changed (each version read through the SHA cache). `readVersion(collection, id, commit)` returns an `EntryDocument` with status `read-only`, read with the same reader as today.
- **Viewing** (call H3). An earlier version opens in the editor's own form, read-only, as a viewer sees it. A line above the title names the fields that differ from now, each a link to its field, and each of those fields says "Changed since this version" in its description: words, no colour.
- **Restoring.** "Restore this version" loads that version's raw values and body into the editor as unsaved changes, and nothing is written yet. In local and GitHub modes, Save or Publish writes them through the usual splice and checks. In the cloud, autosave makes it a draft, as spec §7.4 says, and it publishes or goes to review like any draft. The change set's summary says "Restore “Harbor at dawn” to the version of 14 October", with a `Vesper-Restored-From` trailer, so history can say so later. A restore never moves the file back to an old path. If a restored version uses an image that has since been removed, the save is refused in plain words, naming the image.

**Where it lives.** "History" in the editor's "…" menu, as §10.3 lists it, opening a drawer (the Details and notes pattern). The drawer lists versions newest first: when (in the site's time zone, as dates are shown), who, and the summary. Each row is a link to `#/c/<collection>/e/<id>/history/<commit>`, so a version survives a reload with no rewrite rules. "Show earlier" loads the next page. While a version is open, the editor's bar has a back link ("Back to the current version"), the version as status text, and "Restore this version" as the one primary button, in Save's place.

**Keyboard and screen readers.**
- History is a menu item. The drawer is modal: focus goes to its heading, Tab moves through the versions, and Escape returns to the "…" button.
- Each version's link has a full name: "14 October 2026, 3:20 pm, Jeremy Bise: Update “Harbor at dawn” in Blog posts".
- Opening a version focuses the screen's heading, as every screen does, and the heading names it: "Harbor at dawn, version of 14 October 2026, 3:20 pm".
- Fields are read-only, not disabled, so they stay in the Tab order and their values can be read. The differences line is a list of links that move focus to each field, as the error summary's do.
- After a restore, focus returns to the heading, and the status announces "Restored the version of 14 October. Not saved yet." (in the cloud, "Draft saved" follows, as usual).

**Tests.**
- Core:
  - history over the memory adapter, over a temporary git repository (local), and over the fake GitHub: newest first, authors from the author or the trailers, a move followed, paging;
  - a `file()` entry's versions filtered to its own changes;
  - restoring through `ContentService` gives the earlier values, spliced, and refuses a missing image.
- Contract: `runCloudContract`'s new cases, against the fake cloud here and the real API in the cloud's repository.
- Admin (jsdom): the drawer, a read-only version, the differences line and its links, restoring into unsaved changes, and axe.
- e2e:
  - `github`: publish twice, open the first version, restore and publish; the bare repository's file equals the first version's bytes when nothing else changed;
  - `cloud`: a restore becomes a draft;
  - `studio`: the throwaway site copy is made a git repository of its own, with one commit, then saved and restored. A unit test checks that a folder outside any repository gets no History item.
- Docs: a "History" page under Content, and the integration's README.

**Size.** Large: about 12 commits here (storage, three adapters, the contract, services, the drawer and the version view, tests, docs), plus the history endpoints in the cloud's repository.

**Risks.**
- GitHub's rename detection misses a move whose file changed a lot. History then stops at the move; a move made by the studio rewrites only links, so it should be found.
- Old versions can hold text removed on purpose (a phone number published by mistake). History shows them to everyone who can open the studio, as GitHub already shows them to everyone with access to the repository. The docs should say that removing something from history is a git task.
- Rate limits in GitHub mode: one GraphQL request per 20 versions, plus one per move, with bytes cached by SHA.
- Scheduling (Phase 4.5) publishes by rebuilding, with the date already saved in the entry (D18), so History shows the save that set the date, not the moment it went live. That save's summary should name the schedule ("Schedule “Open house” for 3 November") so the list reads well.

**Free or paid** (call H1). Free in local and GitHub modes, and part of the cloud: Jeremy's call, 2026-10-21.

**Calls.**
- **H1. Free or paid.**
  - (a) Free in local and GitHub modes, and part of the cloud. Recommended: it's git's own data, read with the editor's own sign-in, and costs the cloud nothing in those modes. The paid parts stay what only the cloud does: restore as a draft, review.
  - (b) Cloud only, as spec §7.4 places it. Local and GitHub users keep git's own tools.
- **H2. Local mode without git.**
  - (a) No History item. Recommended: an Astro site without git is rare, and git is history.
  - (b) Vesper keeps a copy of each save in `.vesper/history/`, which duplicates git and needs pruning.
- **H3. How an earlier version is shown.**
  - (a) The entry's own form, read-only, with the fields that differ named and marked in words. Recommended: editors see content, not file syntax, and every widget already has a read-only state.
  - (b) The two files' text side by side, as the cloud's conflict compare does (`ConflictCompare`). Cheaper, but it's YAML and Markdown source.

### 3. Inline code in one-line Markdown fields

**Seen.** The compact Markdown editor turns code off (`code: false` in `packages/admin/src/widgets/markdown.tsx`), so a value with backticks loses its code span, text and all: Tiptap's parser drops it, the round-trip check compares two parses that both lack it, and the field opens without it (corrected 2026-10-21; this first said the field fell back to plain text, and step 1's outcome has the fix). vespercms.com's home page writes `src/content.config.ts`, `markdoc.config.mjs` and `meta()` as plain words for that reason (DECISIONS.md, "vespercms.com is a plain Astro site edited with Vesper"; CLAUDE.md has a rule for it). The site renders these fields with micromark, which already turns backticks into `<code>`.

**Design.** Turn on Tiptap's `code` mark in the compact editor, in inline and multi-line fields alike, and add a Code tool after Italic, with the body editor's icon, name, ⌘E shortcut and tooltip. The round-trip check stays: a value the editor can't write back as it is still falls back to plain text. (A code span holding a backtick, written with a double fence, turned out to round-trip.) Nothing is rewritten until someone edits the field. Then vespercms.com's home copy gets its code formatting, edited in the studio as a check, CLAUDE.md's rule keeps only its "no unions" half, and `content/fields.mdoc` says the compact editor has code.

**Where it lives.** One more tool in the field's own formatting toolbar. Icon-only formatting tools are already the §10.4 exception for this editor and the body's.

**Keyboard and screen readers.** The tool is a toggle in the field's toolbar: one Tab stop, the arrow keys along it, and Escape from the text reaches it. It's named "Code", with `aria-pressed`, `aria-keyshortcuts`, and the tooltip "Code ⌘E" on hover and keyboard focus. ⌘E (Ctrl+E) toggles it from the text. Screen readers read code as text; NVDA names it when formatting reports are on.

**Tests.** Widget tests: a value with code opens in the editor, not the fallback; code is toggled by key and by the tool; an unchanged value isn't rewritten; a value with a backtick inside code falls back; axe. The `site` e2e project already renders the home page.

**Size.** Small: two or three commits (the widget and its tests, then the site's copy, the docs and the rule).

**Risks.** Tiptap's serializer with code beside bold or links. The round-trip check catches anything it can't write back, so the worst case is the plain-text fallback, never changed content.

**Free or paid.** Free.

**Calls.**
- **C1. Which fields get code.**
  - (a) Every Markdown field. Recommended: backticks are core Markdown, and every common renderer (micromark, marked, remark) handles them.
  - (b) Opt-in, with `fields.markdown({ code: true })`. A field that shouldn't have code stays as it is, but every site that wants it has to find the option, vespercms.com included.

### 4. Duplicate an entry, and copy links

**Seen.** A new docs page that looks like an existing one starts empty, so its fields are retyped. Pointing a colleague at an entry means copying the address bar, and the page's own address means opening it with View on site first. Spec §10.3 puts "duplicate" and "copy link" in the editor's "…" menu. The design pass listed both as not built.

**Design.**
- **Duplicate** opens a copy as an unsaved new entry, at `#/c/<collection>/e/<id>/copy`:
  - every raw value and the body are copied, and the title gets " (copy)";
  - fields that hold the entry's own address (the `slug` widget's) are cleared, so the copy gets its own, and the file name comes from the title at the first save, as for any new entry;
  - images are shared, never copied, and keep their focal points and crops;
  - in the cloud, the first save is by hand, as for any new entry (DECISIONS.md).

  Saving sends `copyOf: { id, version }` with the new entry. The service reads the original at that version, splices the edited values into its text, and writes the result at the new path (`expectedVersion: null`). So the copy keeps the original's comments, key order and body bytes, through `writeEntryFile` like any save. The services run in the browser in GitHub mode and the cloud, so the cloud's contract doesn't change. In a tree collection the copy goes right after the original among its siblings, in one change set with the folder's `_order.yaml` (`PageService`). In a `file()` collection it's appended as new items are. Singletons have no Duplicate.
- **Copy page address** copies the entry's page address: the one View on site opens, with Astro's `site` in front when it's set, so a link copied in local mode is the live one. It's offered only where View on site is.
- **Copy editing link** copies the studio's address for the entry (`/admin/#/c/<collection>/e/<id>` under Astro's `base`), which survives a reload on any host. In GitHub mode and the cloud, a colleague who opens it signs in and lands on the entry, as the review emails do.
- After a copy, the bar's status text reads "Link copied" for a few seconds (it's a polite status, so it's announced): no toast. Where the Clipboard API isn't there (a site served over plain `http`, or a refused permission), a small dialog shows the link in a read-only field, selected, with "Press Ctrl+C to copy" (⌘C on a Mac).
- **Function-form URLs** (the 2.6 follow-up). They have no View on site today, and would have no Copy page address. GitHub mode and the cloud already load `vesper.config.ts` in the browser, so the editor can run the function there, and in local mode the dev API can answer.

**Where it lives.** The editor's "…" menu, which then reads: View on site, Copy page address, Copy editing link, Duplicate, History, then the danger items (Discard draft…, Delete…). The outline's row menu gains Duplicate. Phase 4.5's Schedule dialog may want this menu too, so its place is agreed with that design. No new buttons or colours.

**Keyboard and screen readers.** Each is a menu item with an icon beside its words. Duplicate moves to the copy's screen, whose heading takes focus ("New blog post, a copy of Harbor at dawn"), and the status reads "Not saved yet". The copy items keep focus on the "…" button and announce "Link copied". The fallback dialog puts focus in its selected field.

**Tests.**
- Core: a copy splices into the original's text (comments and order kept, only the changed values differ); a tree copy is placed after its original in one change set; a `file()` copy; slug fields cleared; a copy needs edit access at its new path (`changeAccess`).
- Admin (jsdom): the menu items per mode and entry kind, the copy's status, the clipboard and its fallback, and axe.
- e2e: duplicate and save in `studio` (the new file checked byte for byte against the original, less the changed lines) and in `github` (one commit).

**Size.** Medium: about 6 commits.

**Risks.** A field that must be unique but isn't a slug (an external ID, say) gets copied. The schema's own refinements, or the build, catch it. A later hint (`.meta({ copy: false })`) could clear it, if a site needs one.

**Free or paid.** Free.

**Calls.**
- **D1. What a copy starts as.**
  - (a) An unsaved new entry with every value copied, " (copy)" after its title, and slug fields cleared. Recommended: nothing is written until the editor saves, as with any new entry.
  - (b) The same, but marked `draft: true` when the collection has a boolean `draft` field. Safer against publishing by accident, but surprising when a copy saved on purpose doesn't appear.
  - (c) Saved at once, then opened. One step less, but the folder fills with abandoned copies.
- **D2. A page with subpages, in a tree.**
  - (a) The page alone. Recommended: copying a section is rare, and it would be a move-sized change set.
  - (b) Also "Duplicate with its subpages".

### 1. Fields that are easy to scan

**Seen.** As measured above. Spec §10.2's principle "typography and space do the work, not boxes" is what the nesting breaks: the form's structure is drawn with frames, and its type has one level.

**Design.**
- **Sections.** A top-level object or list (the `group` and `repeater` widgets, at the first level) becomes a section:
  - a hairline above it;
  - its legend in `text-heading-3`, holding an `h2`, as GOV.UK puts a heading inside a legend;
  - its description beneath.

  Screen reader users can then move through a long form by heading, which they can't today. Plain fields between sections keep `text-label`. Sections get `gap-10` (40px) above them, and plain fields keep `gap-6` (24px) between them.
- **No frames inside the form.** Objects lose their frame. A nested object gets an indent guide instead: a hairline on its left and `pl-4`, with its legend in `text-label`. The image and geo widgets keep their frames, since those hold a preview or a map. No new token.
- **Items as rows.** A list of objects or images shows each item as one row:
  - **The item's name.** It comes from the field a `summary` hint names. Without a hint, it's the first of `title`, `name`, `label`, `heading` and `text`, as `itemSummary` does now. Failing both, it's "Point 3", from the item's own label. An image item shows its alt text, or else its file name, with a 40px thumbnail through `useFileUrl`.
  - **A muted detail after it.** The count of its first nested list ("3 points"), or else its second text value, truncated. A problem shows as text after it: "1 problem" in `danger`, "1 note" in muted text (notes stay text, never badges).
  - **A "…" menu**, the overflow button §10.4 allows: Move up, Move down, Duplicate and Remove, with Remove as the danger item. Duplicating an item is new and costs little.
  - **Opening in place.** The row's name is the trigger of the kit's `Disclosure`, with its chevron. Open, the item's fields sit under the row behind the indent guide.
- **Which items are open** (call F1). All are closed when an entry opens, except:
  - a new item, which opens with focus on its first field;
  - items holding a field a refused save names, since the error summary's links open every item on the way to that field, as they open Details now;
  - an item a notes drawer's Go to field leads into.

  A quiet "Open all" button, which becomes "Close all", sits on the list's legend line once a list has three items, for reading everything through.
- **Closed items stay in the page.** The kit's `Disclosure` already closes its panel with `hidden="until-found"`, so the browser's find opens the item that matches, where the browser supports it. Elsewhere React Aria falls back to `hidden`, and find misses closed items. Nothing unmounts, so the editors inside keep their state and their undo history. The page renders the same controls it renders today, so mounting costs no more.
- **Stable identity.** Each item gets an id when the entry loads, as the tables design gives rows, so the open state and focus follow an item through a move. The ids never reach the file.
- **The `summary` hint**, `.meta({ summary: 'question' })` on the list, joins `META_KEYS` in `packages/core/src/schema/walk.ts`. It's the same word Markdoc tags use for their frames' summary, and it's needed only when the guess picks the wrong field.
- **Labels inside lists.** An item no longer says "Item 2 (required)": it's named by its content, and an item never says "(required)", since it either exists or doesn't. The rest of the required question is call F2.
- **Other lists.** Lists of numbers or dates keep one control per item, and the "…" menu replaces their three buttons. Lists of strings, choices and references already have their own widgets (tags, multiselect, references) and don't change. A custom widget that claims a list, like the playground's store hours, isn't affected.
- Markdoc tags' settings dialogs use the same widgets, so item 4's list attributes get rows from this.

Estimated effect on vespercms.com's home page: with every item closed, the form is the title, the summary, the hero (two fields and two action rows) and five section rows, under 2,000px. To be measured once it's built.

**Where it lives.** In the form itself. There's no new screen, panel or colour: rows are `surface-raised` with hairlines, a problem is `danger` text, and the indent guide is `border`. The "…" menu is §10.4's overflow exception. Dragging is call F3.

**Keyboard and screen readers.**
- A row's name is a button with `aria-expanded` and `aria-controls` (React Aria's `Disclosure`), named by the item and its detail: "No second schema, 3 points". Rows of a top-level list sit in `h3`s, so heading navigation reaches each section and each of its items. Deeper rows are plain buttons.
- Enter or Space opens and closes a row. Alt+↑ and Alt+↓ on a row move its item, as in the page outline, announced in the list's polite status ("Moved No second schema to position 2 of 5."), with focus staying on the row.
- The "…" button follows its row in the Tab order. Shift+F10 on a row opens it too, as "Table actions" does on a cell.
- Remove moves focus to the next row, or else the previous one, or else "Add …", and is announced, as now. Add opens the new item, focuses its first field and announces "Added point 4."
- With every item closed, the home page's Tab stops in the lists fall from 66 move and remove buttons plus every field to two per row (its name and its "…").

**Tests.**
- Unit: `itemSummary` with and without the hint, image items, the fallback name; ids survive moves and removals.
- Admin (jsdom):
  - rows named by their content;
  - opening and closing, and Open all;
  - Alt+↑/↓ with its announcement and focus;
  - the menu's items and Duplicate;
  - focus after Remove and Add;
  - a refused save opening the item with the error, and Go to field opening nested items;
  - closed panels are `hidden="until-found"`;
  - sections are `h2` and top-level rows `h3`;
  - axe with rows closed, one open, and the menu open.
- e2e (`studio`, keys only), on the playground's pages: move a section with Alt+↓, edit a field inside a point, remove one and add one. The file is checked byte for byte: only the changed lines differ. axe with an item open.
- Docs: `content/fields.mdoc` describes lists and the `summary` hint. `vesper agents` lists the hint (its snapshot and `apps/site/AGENTS.md` regenerated).

**Size.** Medium: about 7 commits (sections and frames; rows and their menu; the open state and reveal on errors; the hint through core and the manifest; tests; docs and the agent guide).

**Risks.**
- Someone who liked seeing everything at once. Open all covers that, one click per list.

**Free or paid.** Free.

**Calls.**
- **F1. How list items show.**
  - (a) Rows, closed when the entry opens, opening in place. Recommended: the entry stays one page, the error summary and the browser's find still reach every field, and it's the disclosure pattern screen readers already know.
  - (b) Rows that open an item in a view of its own, replacing the column, with a trail ("Home › Sections › No second schema"), as Sanity now does. Deep lists stay calm, but the rest of the entry is out of sight while you edit, Back then means two things, and a refused save has to send people into the right view.
  - (c) Rows that open an item in a dialog or drawer, as Sanity did before. Nested lists then stack dialogs.

### 2. The entry list beside the editor

**Seen.** The back-and-forth Jeremy described: going from one entry to the next is a full screen each way. **Design** (call L1's (b)).
- **When.** At 80rem (1280px) and wider, the editor screen shows its collection's list in a pane on the left, 18rem wide, beside the 720px column. The pane, a 2.5rem gap and the column fit in the top bar's 72rem container (65.5rem plus its padding), and the two are centred together. Narrower, including 200% zoom on most laptops, nothing changes: the column alone, with its back link. That's above the Details drawer's 68.75rem, so Details still opens as a drawer over the right side whenever the pane shows.
- **What it shows.**
  - A flat collection, or a `file()` one: a search field, then the entries. Each shows its title with the list screen's muted "who · when" beneath, and its status as text when it isn't plainly published ("Draft"). Sorting and the status filter stay on the list screen.
  - A tree collection: the outline, read-only, with expanding, collapsing and links. Moves, order and the row menus stay on the Pages screen, so `PageService`'s rules don't change.
  - A singleton: no pane, since there's nothing to list.
  - "New post" (the collection's own word) as a quiet button at the pane's foot. The editor's one primary button stays Save or Publish.
- **Moving between entries.** Opening another entry swaps the column. The pane keeps its scroll, search text and open rows for the visit. Unsaved changes ask first, through the leave dialog the router already has ("Leave without saving?", `app/App.tsx`). In the cloud, autosave has already made a draft, so nothing asks.
- **Keeping up.** After a save, the pane shows the new title and status. A deep link straight into an entry loads the list for the pane: the same summaries the list screen reads, through the SHA cache in GitHub mode and the cloud. In the cloud, the pane shows what the list shows (`shownTo`, `fileAccess`).
- **Showing and hiding** (call L2). Beside the editor bar's back link, a quiet "List" button with the sidebar icon beside the word shows and hides the pane (`aria-expanded`, `aria-controls`). It appears only at the pane's width. The choice is kept per viewer in `localStorage`. The back link still goes to the full list screen.
- **Navigation levels.** On the editor screen the pane is the only navigation, since the bar holds the entry's controls. The list and Home screens don't change, so §10.4's "two levels at once" holds.
- **Phase 7's preview** (side by side) takes the pane's place while it's on: editor and preview, never three columns.

**Where it lives.** The editor screen, on wide screens only. The pane is `surface` with a hairline on its right. The current entry has `glow-selected` and `aria-current="page"`, in that glow's named place ("the current item"). There's no new colour. It departs from §10.3's single column and §10.2's "not permanently visible": the dated note is in DECISIONS.md ("The entry list sits beside the editor on wide screens"), and spec §10.2 and §10.3 say so.

**Keyboard and screen readers.**

### 4. What's left for Markdoc tags

**Seen.** Phase 2.5 met its five criteria (its outcome, below), and nothing in its design is unbuilt. What's left came later, or is v2 in the spec:
- **Tables in the writing view.** Designed and decided (item 1 of "Studio additions from dogfooding", calls T1 to T4), and step 3 of that section's order. Not built. Task lists, footnotes and links with titles are noted to follow it.
- **List and object attributes are edited as raw YAML, and an edit puts them on one line.**
  - A Markdoc attribute of type `Array` or `Object` gets the raw YAML field (`packages/core/src/markdoc/fields.ts`), since Markdoc says nothing about what's inside it.
  - The corpus has a real one. Jazzy's `faq` tag has `items`, a list of `{ question, answer }`, on 9 pages, written one question per line (`edibles-calculator.mdoc` has 7).
  - `editMarkdocTag` replaces the attribute's whole value with `markdocValue`'s output, which is one line. So changing one answer rewrites all seven questions as a single line of about 2,200 characters. The page is the same, but the change is the whole list, against DECISIONS.md's "No unrelated diff".
  - `editJsxTag` writes an MDX prop's array with `JSON.stringify`, so it has the same problem.
- **Variables, functions, `{% if %}` and annotations** are protected source chips, as §6.5.1 says for v1. Outside the playground's fixtures, which test them, no content in this repository or the corpus uses a variable, and `{% if %}` appears only on vespercms.com's Markdoc docs page, which explains it.
- **The real component inside a block** (§6.5.1's v2) is Phase 7, through the dev server and preview deployments.
- **The caret.** On a Mac, with an inline chip itself selected, ⇧⌘← leaves a caret before it (DECISIONS.md, "⇧⌘← and ⇧⌘→ beside a chip are the browser's", still open).
- **Size of the editor's code.** The body editor (512 KB) and the body checks (513 KB) are lazy chunks over Vite's 500 KB warning. Neither is in the first load.

**Design.**
- **List and object attributes as fields** (call M1). A hint in `vesper.config.ts` gives such an attribute its shape as a Zod schema, as MDX components' `props` already do (spec §6.5.2):

  ```ts
  markdoc: {
    tags: {
      faq: {
        label: 'FAQ',
        attributes: {
          items: {
            label: 'Questions',
            schema: z.array(z.object({ question: z.string(), answer: z.string().meta({ widget: 'textarea' }) })),
          },
        },
      },
    },
  },
  ```

  The settings dialog then renders it with the frontmatter's widgets, item 1's rows included. Markdoc's own validation stays the authority when saving. The schema only shapes the form and checks it as a field is checked. Without a hint, the raw YAML field stays.
- **Writing items, not the whole list** (call M2). When a value was written one item per line, as Jazzy's is:
  - a changed item rewrites only its own line;
  - a new item is written in the same layout after the last;
  - a removed item goes with its line;
  - a moved item moves its line as it is.

  Any other layout (one line, or one the scanner doesn't recognize) is written whole, as now. As with tables, the result is parsed again and must read back as the intended value, or the save is refused. This lives in core beside `editMarkdocTag`, and `editJsxTag` gets the same for array props.
- **The caret fix,** small, on its own.
- **Not now** (call M3): variables and conditions as more than chips, and component rendering, which is Phase 7.

**Where it lives.** In the tag's Settings dialog, as now, with the hint in `vesper.config.ts`. No new interface.

**Keyboard and screen readers.** The dialog's lists use item 1's rows and keys. Nothing else changes.

**Tests.**
- Core:
  - the hint's schema becomes field models;
  - item splicing: a change, an addition, a removal and a move each touch only their lines;
  - one-line values are written as now;
  - a refused read-back;
  - the Jazzy corpus with a hint for `faq`: changing one answer in each of the 9 tags changes one line.
- Admin (jsdom): a dialog with a list attribute; axe.
- e2e (`studio`): a new playground FAQ tag with a list attribute, edited by keys, with the file checked byte for byte.
- Docs: `content/markdoc-and-mdx.mdoc`, the integration's README, and `vesper agents` (the hint).

**Size.** Small to medium: about 5 commits (the hint and its fields; item splicing in core; the fixture and tests; docs). The caret is one more.

**Risks.**
- Markdoc's object syntax has variants (quoted and unquoted keys, spacing inside braces). The scanner must agree with Markdoc's parser, or the value is written whole as now, so it's never wrong.
- A Zod shape in `vesper.config.ts` leans toward field definitions there, which §6.4 rules out for collections. The precedent is MDX props, which also have no other source.

**Free or paid.** Free, as the body editor is.

**Calls.**
- **M1. List and object attributes.**
  - (a) A Zod `schema` hint per attribute in `vesper.config.ts`, as MDX props have. Recommended: Markdoc can't describe what's inside, and this is the one place Vesper already takes a shape for a component.
  - (b) Guess the shape from the values in the file: Jazzy's items all have `question` and `answer`. No config, but a new tag has nothing to guess from, and one odd item changes the form.
  - (c) Keep raw YAML, with M2's item-by-item writing so edits at least stay small.
- **M2. Writing a changed list.**
  - (a) Item by item when it was written one per line, else whole, as now. Recommended: one changed answer is one changed line, as "No unrelated diff" asks.
  - (b) Always whole, as now.
- **M3. Variables and conditions.**
  - (a) They stay protected chips until a site uses them. Recommended: no real site's content in the corpus uses a variable.
  - (b) A variable picker in "/" from the config's variables, and `{% if %}` as a labelled frame with its condition as text, now.

## Blocks: lists of different kinds (design)

Proposed 2026-10-26, from a review of what moving thosegeeks.com off EmDash would take. **Jeremy took (a) on every call the same day, and it was built that day** (outcome at the end). DECISIONS.md records the calls ("Blocks are a discriminated union of objects"), and spec §6.2's mapping table matches.

**Seen.**
- **What sites write.** A page builder in Astro is a list whose items are different kinds, told apart by one key:

  ```ts
  sections: z.array(z.discriminatedUnion('type', [cardGrid, faq, showcase, servicesGrid])).default([]),
  ```

  thosegeeks.com's `sections` field has 11 kinds: card grid, tag list, FAQ, stats, rich text, showcase, a label card for the hero, and four that list another collection (services, featured work, quotes, recent writing). Its home page and service pages are built from it. The 420 landing page has six blocks of four kinds: three card grids, a showcase with a screenshot, rich text and the label card. EmDash edits it as a block list (`~/code/thosegeeks-emdash/seed/seed.json` has the kinds).
- **What Vesper does.** `unionField` in `packages/core/src/schema/walk.ts` makes any union that isn't string literals `kind: 'unknown'`, so the whole list is one raw YAML box (`content/fields.mdoc`, "Raw YAML fields"). vespercms.com avoids it with sections of one shape, and CLAUDE.md's rule against unions on that site exists for this reason.
- **Markdoc tags aren't the answer here.** Each kind could be a tag in the body, and the `schema` hint gives its lists rows. But a tag attribute can't use the image picker and its path doesn't go through Astro's image pipeline, and a template can't place one block somewhere else: thosegeeks lifts its label card into the hero, and puts a proof band before the first tag list or FAQ. Tags stay the way to put components inside prose.
- **What Zod gives,** checked against the installed Zod 4.6.7 through `astro/zod`:
  - `z.discriminatedUnion('type', [...])` has `def.type: 'union'`, `def.discriminator` and `def.options`, and each option's `.meta()` reads as usual.
  - A missing or unknown `type` is one issue: `invalid_union`, `note: 'No matching discriminator'`, at `[…, index, 'type']`, listing the allowed values. A known `type` reports that kind's own issues at their own paths.
  - A plain `z.union` of objects reports `invalid_union` with every option's issues nested inside it, so its messages can't point at a field.
- **What already works.** A block is a plain map in the file, so saving needs nothing new: the patch diff and the YAML and JSON writers already splice, move and copy list items as whole maps (DECISIONS.md, "A moved list item moves its text as it is"). The rows that open in place (`RepeaterWidget` in `packages/admin/src/widgets/group.tsx`) already name, move, copy and remove items. The cloud needs nothing either: drafts are checked with the site's own schemas (`_vesper/schemas.js`), and grants match file paths.

**Design.**
- **In the field model.** A new kind, `union`, for a discriminated union whose options are all objects, each holding the key as one string literal:

  ```ts
  { kind: 'union', discriminator: 'type', variants: [{ value: 'faq', label: 'FAQ', description?, summary?, children: FieldModel[] }] }
  ```

  - A variant's `label`, `description` and `summary` come from `.meta()` on its object, as a field's do. Without a label, it's the value in sentence case: `card_grid` is "Card grid".
  - The key itself isn't among a variant's `children`: it is the variant.
  - Children's paths are value paths, as an object's are: `['sections', '[]', 'heading']`, whichever variant holds it.
  - Anything else stays raw, with its reason: an option that isn't an object, a key that allows several values or none, a union as an option, `unionFallback`. A plain `z.union` of objects that share a string-literal key gets a diagnostic in the terminal: "Use z.discriminatedUnion('type', …) for this field to get a control in the studio" (call B1).
- **One place that knows variants.** Core gains `fieldChildren(field)` (every variant's children, for walks over a schema) and `childrenFor(field, value)` (the variant the value names, for walks over an entry). Every walker that reads a field's `children` switches to one of them. Found today: widget resolution (`widgets/resolve.ts`), the manifest's ratio and contrast checks (`manifest/build.ts`), the field accessibility rules (`a11y/fields.ts`), the field checks (`studio/field-checks.ts`), link rewriting (`studio/links.ts`), search's field marks (`search/fields.ts`), the issue target (`packages/admin/src/editor/target.ts`) and `vesper agents` (`packages/astro/src/node/agents.ts`); a search for `.children` finds the rest when building. The union model has no `children`, so a walker that hasn't learned variants skips them rather than misreading them.
- **A list of unions: blocks.** The repeater, with these differences:
  - **Add.** "Add {item}" (from the list's label, as today: "Add section") opens a menu of the kinds, each with its description under its name. Choosing one adds the kind, its key first, with its fields' defaults as a new entry gets them, at the end. Its row opens and its first control gets focus. A list of one kind adds it directly.
  - **Add below.** Each row's "…" menu gains "Add below", a submenu of the same kinds (call B3).
  - **Rows.** A row is named by its kind, with its summary as the muted detail: "Card grid · This industry has rules. Your website should already know them." The summary is the kind's `summary` field, else a title-like field, else its first text, as `itemSummary` already finds it. On a page the order of kinds is what someone scans for, and kinds are short names.
  - **Change to.** The "…" menu gains "Change to", a submenu of the other kinds (call B4). Fields whose key and kind are the same in both keep their values, and the rest are dropped. When anything would be dropped, a confirmation names those fields. Dropped values are kept for the visit, so changing back before saving brings them back.
  - **An unknown kind.** An item whose key the schema doesn't list, or that has none, is a row named "Unknown kind: {value}" holding the raw YAML field for that item, with "Change to" to fix it. The save is refused by the schema, as now, and the message for a missing or unknown key becomes "Choose a kind for this {item}." instead of "This value doesn't match any of the allowed shapes."
  - **At most.** At the list's `max`, Add is disabled and a line under it says so: "At most 20 sections." This applies to every list, which doesn't check `max` today.
- **A single union: a choice of kinds** (call B2). The field's group starts with the kinds, as radio buttons for four or fewer, otherwise a select, labelled "Kind", then the chosen kind's fields. An optional field adds "None". Changing the kind works as "Change to" does.
- **Inside Markdoc and MDX.** A tag attribute's `schema` hint and an MDX component's `props` go through the same walk, so a union there gets the same control in the settings dialog.
- **Nesting.** A kind may hold its own blocks, such as a two-column kind with a list in each column: rows open inside rows, as lists of lists already do.
- **On the site.** Nothing from Vesper (call B6). The docs show the pattern:

  ```astro
  ---
  const kinds = { card_grid: CardGrid, faq: Faq, showcase: Showcase };
  ---
  {entry.data.sections.map((block) => {
    const Block = kinds[block.type];
    return <Block {...block} />;
  })}
  ```
- **Docs and rules.** `content/fields.mdoc` gets a "Blocks" part and a row in its table, and discriminated unions of objects leave its "Raw YAML fields" list. `vesper agents` describes a union by its key and each kind with its fields. CLAUDE.md's rule against unions on vespercms.com narrows to plain unions.

**Where it lives.** In the form, as a list's rows. No new screen or panel. Add stays a secondary button with its words and icon, and kinds are words with a description, not icons (call B5). The kit's `Menu` gains a description line under an item's name and submenus (React Aria's `SubmenuTrigger`); it has neither today.

**Keyboard and screen readers.**
- Add opens a menu: the arrows move through the kinds, typing jumps to one by name, Enter adds it, and Escape returns to Add. The new row opens with focus on its first control, announced as "Added FAQ, section 4 of 4."
- In a row's "…" menu (Shift+F10 on the row, as now), "Add below" and "Change to" open their submenus with → and close them with ←. After "Change to", focus returns to the row, announced as "Changed to Stats. Heading kept; Cards removed."
- A row's accessible name is its kind, then its detail, then its problems, as now: "Card grid, This industry has rules…, 1 problem".
- The single choice is a radio group or select labelled "Kind" inside the field's fieldset, so it's heard after the field's name.
- Alt+↑ and Alt+↓, Open all, and `focusWhenShown` opening closed rows work unchanged.

**Tests.**

From GitHub's, Cloudflare's, Microsoft's and OpenCage's docs, checked on 2026-10-20 (sources go into DECISIONS.md with the calls):
- **The app's commits are Verified.** A commit made with an installation token is signed by GitHub and shown as Verified, as long as it sets no author, committer or signature of its own. That satisfies a rule requiring signed commits. Setting the editor as the author would lose it, which settles §7.3's bot author. Phase 3's open item about unsigned commits is GitHub mode's alone.
- **Connecting a repository needs the installer's own GitHub sign-in.** GitHub warns that the `installation_id` it returns after an install can be spoofed. The fix is a user token for whoever installed the app, then `GET /user/installations` to confirm the installation is theirs. The install link carries a `state` through. Only the person connecting the repository (usually the agency's developer) needs a GitHub account, never the editors.
- **Branch rules can be read before publishing.** Rulesets come from `GET /rules/branches/{branch}`, with Metadata read. Classic protection comes from `GET /branches/{branch}`, with Contents read. A refused push is a 422 whose message isn't stable enough to parse.
- **Deploy status** needs three read-only permissions: commit statuses, checks and deployments. Some hosts report through deployments.
- **Hosts and bot authors.** Netlify holds a private repository's deploys from authors it doesn't recognize. It recognizes GitHub Marketplace bots, and auto-approve or a build hook gets round the hold. Vercel deploys a private repository's commit only when its author has access to the project. Its docs don't mention app bots, and a 2024 forum thread shows a bot's commits blocked. Cloud editors have no GitHub accounts, so no author would be recognized anyway. The bot at least is one identity a team can approve.
- **Email Service is still in beta** (public since April 2026):
  - it needs Workers Paid, and the sending domain must use Cloudflare's DNS;
  - 3,000 emails a month are included, then $0.35 per 1,000;
  - new accounts get a daily quota that isn't published and grows with reputation.
- **Limits are far away:** 10 GB per Durable Object and per D1 database.
- **Microsoft sign-in** for any organization needs the issuer checked against the token's own tenant. Publisher verification isn't required for sign-in alone. ### How it works

**Accounts and sessions** (cloud-app and cloud-api, §7.2).
- People sign in with an email link, Google or Microsoft. Identities join on a verified email address.
- Dashboard sessions follow Taproot: a random 32-byte token in an `HttpOnly`, `Secure`, `SameSite=Lax` cookie on `app.`, stored as its SHA-256 in D1, 30 days, extended at half life, replaced when someone's role changes. Every form that changes something checks a CSRF token.
- Email links and code exchanges are throttled by email and by IP in D1.
- Nobody signs up in Phase 4 (call 6): an operator script creates the account, and everyone else joins by invite.

**The studio's connection** (§6.9, §7.2).
1. The build writes the project ID and the cloud's addresses into the studio.
2. The sign-in screen offers "Sign in with Vesper", and "Sign in with GitHub" too when GitHub mode is set up.
3. A top-level redirect goes to `app.<domain>/authorize` with the site, a state and a PKCE challenge. The page signs the person in if needed, checks that they belong to the site and that the return address is one of the site's registered origins, and sends them back to `/admin/#/callback` with a one-time code. In the hash, the code never reaches the host's logs.
4. The studio exchanges the code and its verifier at `api.<domain>/token` for an access token: about 10 minutes, for that one site, carrying the person's role and grants. How it stays signed in is call 2.
5. The API checks membership and grants again from D1 on every write. A token alone is never trusted for permissions.

Registered origins are the site's production and preview addresses, plus `localhost` ports for development. Codes go only to them, and the API answers CORS only for them.

**Reading the repository** (the git proxy, §7.3). `CloudStorage` in the studio lists and reads through the API, which reads GitHub with an installation token through `GitHubStorage`. The studio never sees that token. The API caches the tree per commit in the site's Durable Object, and the studio keeps GitHub mode's IndexedDB cache by blob SHA, so a warm visit fetches only what changed.

**Drafts** (§7.4). One Durable Object per site (D15) holds drafts, reviews and the repository cache in SQLite.
- A draft is the file the save would write: the same splice and the same checks as a local save, kept with the version it was based on. Publishing is then exactly what local mode would have written. §8.2's sketch stores parsed data and a body instead; the file's own text keeps round-trip fidelity (§6.5) in one place.
- The studio autosaves a second after typing stops. The status is text: "Draft saved", or "Saving…".
- Uploads from a field wait in R2 under the site's own prefix until the draft is published, then go into the same commit, as `ChangeSet.defer` does in GitHub mode. A discarded draft deletes them.

**Publishing.**
- Someone who may publish chooses drafts and publishes them. The API checks the publish grant on every file, builds one change set with each draft's base version as the expected version, and commits it through `GitHubStorage`: one commit for any number of drafts. Then it clears them.
- The commit's author is the app's bot (§7.3). The editor appears in a `Co-authored-by:` trailer and a `Vesper-Editor:` trailer with their user ID, plus `Vesper-Collection` as today.
- If a file changed on GitHub since its draft began, the studio shows the published version and the draft side by side (§7.4). The editor keeps theirs, now based on the new version, or discards it. Nothing is overwritten silently.
- A branch rule that refuses the push is call 5.
- The accessibility publish gate (§6.18, `a11y.blockPublishOn`) applies to Publish as in local mode. Request review isn't gated: reviewers see the same notes.

**Review** (§7.4). Someone who can edit but not publish sees "Request review" instead of Publish. It sends the chosen drafts to the site's approvers by email and in the studio. An approver opens the review, sees each change beside the published version, and publishes, asks for changes with a comment, or comments only. Editing a draft that's under review updates the review.

**Grants** (§7.5, call 3). A member has a site role (admin, editor, contributor or viewer) and, optionally, grants: a collection, an entry glob, and whether publishing needs approval. `@vesper/core` evaluates them for both sides:
- the API refuses drafts, publishes and reviews outside them, and a move needs a grant at both its old and new place (§6.15.4);
- the studio hides what someone can't do, except where a line helps ("Publishing needs approval").

**Deploy status** (§6.16). After a publish, the studio and dashboard read the commit's statuses and check runs through the API and show "Publishing…", "Live" or "Build failed", with a link to the host's log. With no status at all (a host built by hand), the studio says "Published. It will be live after the site is next built."

**When the cloud is unreachable.** Unsaved changes are written to IndexedDB as they're typed. The studio says "Can't reach Vesper. Your changes are kept on this device, and they'll be saved when it's back." and retries with backoff. A reload with the cloud down keeps them. Signed out, the studio shows no cloud wording at all.

**The dashboard, v1** (§9.1), at `app.<domain>`:
- **Sites:** the list, and Add site (name, production address, preview addresses).
- **Connect repository:** install the GitHub App and choose the repository. The person connecting signs in to GitHub once, so the cloud can confirm the installation is theirs. The page checks the branch's rules and says plainly if publishing straight to it won't work.
- **People:** invite by email with a role and grants; change or remove them.
- **Open studio:** a link to the site's `/admin`.

It's built with `@vesper/ui` and the same tokens and budget as the studio, and every screen passes axe with a keyboard pass.

**Email** (§7.8): sign-in links, invites and review requests, as plain accessible HTML with a text version. The provider is call 7.

**The audit log** (§7.10) records every write from the first day: who, what, which site, when.

**Operator scripts** (§9.2, before the Phase 5 console): create an account, add a site, suspend, and list, run with `wrangler d1 execute`.

## Phase 4.5: Scheduled publish and unpublish (design)

Scope is the §11 Phase 4.5 entry and §6.17, under D18: scheduling is time-correct at build. Any rebuild at or after the time gives the right site, on any host, with or without the cloud, and the cloud's only job is to trigger a rebuild at the exact time. The free half lives here, under MIT: build-time filtering, the studio's Schedule dialog and Scheduled view, unpublish redirects, and the deploy templates' scheduled rebuild. The paid half lives in `vesper-cloud`: exact times through Durable Object alarms, `holdScheduledDrafts`, and each scheduled event's result. This section describes that half at the boundary; its detailed design goes in that repository's PLAN.md. Written 2026-10-21, ahead of time, and Jeremy confirmed its calls that day. **Done when** (§11):

### How it works

**Opting in** stays as §6.17 has it: `schedule: true` on a collection, `{ unpublish: false }`, or mapped names (`{ publishAt: 'publishedAt' }`).
- It gains one optional name, `unpublishRedirect`, which is also the default.
- The fields must be in the collection's schema, since Astro strips unknown keys before the site's code sees them. A scheduled collection without them gets one warning in dev and at build, naming the lines to add (`publishAt: fields.datetime().optional(),`).

**Build-time filtering** (D18; free, every host):
- **One instant per build.** The build reads the time once, at `astro:config:setup`. Every check in it uses that instant: `vesper:content`, redirects, search, the accessibility check and `schedule.json`. `VESPER_BUILD_TIME` (an ISO time) sets it, for tests and for seeing the site as it will be.
- **Three loaders are wrapped.** In builds, `vesper:content` still re-exports `astro:content`. For scheduled collections only, with the instant and each schedule embedded as JSON, it also wraps three loaders:
  - `getCollection(name, filter?)` leaves out entries outside the window, after the site's own filter;
  - `getEntry(…)` returns `undefined` for one, as Astro does for an entry that doesn't exist;
  - `getEntries(refs)` leaves them out.

  Other collections and `render` are untouched. `getTree`, `getChildren` and `getBreadcrumbs` read through `getCollection`, so they follow. A scheduled section page's folder shows as a folder with no page (`url: null`).
- **Still nothing recorded.** CLAUDE.md's rule becomes: production `vesper:content` re-exports `astro:content`, filters only scheduled collections, and never records reads.
- **Sites that read `astro:content` directly** aren't filtered. The build finds them through the URL tracing the accessibility check uses. A built page whose URL belongs to an entry outside its window gets a warning: "/events/harvest-concert/ was built, but it's scheduled for Sat, Oct 31, 8:00 AM. The page reads astro:content; import from vesper:content instead."
- **Sitemaps and feeds.** Vesper builds neither; both are on the not-adopted list. `@astrojs/sitemap` lists the pages Astro built, and a feed made with `vesper:content` reads the filtered list, so both follow without work.
- **References** to a scheduled entry resolve to nothing until it's live, as they would to a missing entry. The docs say so, and the playground's event page already copes with a missing location.
- **Search keeps its own check.** Pages outside the window aren't built now, but the check still covers a site that reads `astro:content`.

**In dev**, scheduled entries stay in `vesper:content` so editors can work on them, and they're marked (call 10). Dev and builds then differ for scheduled collections only. The tree parity test (`/site-tree.json`) uses `pages`, which isn't scheduled.

**When the site next changes.** Every build writes `dist/_vesper/schedule.json`: `{ "version": 1, "builtAt": "…", "next": "…" }`. `next` is the earliest publish or unpublish time after the build's instant, or `null`. It says only when, never what.
- The free tier's scheduled rebuild reads it (call 2).
- The cloud reads `builtAt` on the live site to tell when a scheduled change is live, on any host.

**Unpublishing.** An entry past its `unpublishAt` isn't built, so its URL 404s.
- Hosts that deploy atomically (Netlify, Cloudflare, Vercel, GitHub Pages) drop the old page with the new deploy.
- The SFTP and FTP templates must delete what the build no longer has, or the old page stays on the server (call 4).

**The unpublish redirect** (call 1, as recommended):
- **From the entry's field.** At config setup, the build lists the entries past their `unpublishAt` that have a redirect set. It adds a temporary (302) redirect from each one's URL into the same `cleanRedirects` pass as the redirects file. Chains then collapse, and host rules (`_redirects`, `.htaccess`, nginx) carry it.
- **Nothing in the file.** Nothing is written into `vesper.redirects.yaml`, so there's nothing to undo if the entry comes back.
- **Cleaned against live pages only.** The page keys the pass cleans against leave out unpublished entries; otherwise the redirect would be dropped as "the page wins".
- **On Vercel** it's Astro's HTML redirect page, the universal fallback, because Vercel reads `vercel.json` before the build.
- **The file wins.** A redirect for the same address in `vesper.redirects.yaml` takes priority, with a warning.
- **The field** uses the page picker and stores the page's exact URL. Link rewriting on moves already covers `url`-widget fields.

**The free tier's scheduled rebuild** (calls 2 to 5). `vesper deploy init --target sftp|ftp|hook` writes one GitHub Actions workflow into the repository and lists the secrets to add.
- **Targets.** `sftp` and `ftp` build on push and upload, as §6.16 says. `hook` is for git-connected hosts, which already build on push: it only calls the site's build hook, kept in a repository secret.
- **The scheduled run.** With `--rebuild-every 60` (minutes, at least 5), the workflow also runs on `schedule:`.
  - Its first step fetches the live site's `/_vesper/schedule.json`. It goes on only when `next` has passed, or when the file can't be read.
  - A site then rebuilds once per scheduled change, not every hour.
- **Other triggers.** Every workflow also listens for `repository_dispatch` (type `vesper-rebuild`), the cloud's trigger, and has `workflow_dispatch`, a button for people.
- **Telling the studio.** `deploy init` prints a `rebuildEvery` line for `vesper.config.ts`, which the studio's accuracy line reads (call 5).

**Exact times in the cloud** (paid; described here, designed in `vesper-cloud`):
- **Where the times come from** (call 6): the site's files, read with core's `scheduledEvents` and the manifest. A time set in local mode or by a developer's commit then gets its exact rebuild too. The SiteDO reads them after every publish through the cloud and on GitHub's push webhook, and keeps them with each event's state.
- **The alarm.** The SiteDO keeps one alarm, for the earliest pending time. When it fires, the SiteDO:
  1. publishes any held drafts due then (below);
  2. triggers one rebuild for everything due;
  3. records the result and sets the next alarm.
- **The trigger** is chosen in the dashboard, per site:
  - a deploy hook URL (Netlify, Cloudflare Pages or Vercel), stored encrypted and never shown again in full;
  - or `repository_dispatch` through the GitHub App, which the templates listen for.

  A site with neither gets no exact times, and the studio's line says it goes live at the next build.
- **Results.** An event goes from waiting to rebuild started, and then to one of:
  - live, when the live site's `schedule.json` shows a build after the time;
  - failed, when the host reports a failure or there's no such build within 30 minutes.

  The dashboard lists recent results, and the studio's Scheduled view shows the upcoming events' state.
- **`holdScheduledDrafts`** (call 7) is a site setting in the dashboard. It's for public repositories, where a future post committed to git can be read early.
  - Scheduling then keeps the drafts in the SiteDO instead of publishing them.
  - At the time, the alarm publishes them as Publish does (one commit, by the app's bot, crediting every author) and triggers the rebuild.
  - Nothing is published if a held file changed in git since, or if the person who scheduled it can no longer publish there. The Scheduled view says why, and that person gets an email.
  - Only the publish waits. An unpublish time is a plain field, filtered at build.
- **Protocol,** in core, with the fake and `runCloudContract`:
  - `GET /sites/{site}/schedule`: the trigger's kind, whether drafts are held, whether the repository is public, and each upcoming event's state;
  - `POST /sites/{site}/schedule` with `{ drafts, at }`: holds drafts until a time, with Publish's grants and checks;
  - `DELETE /sites/{site}/schedule/{id}`: a held draft goes back to being a draft.

## Phase 3: GitHub mode (design)

Scope is spec §6.8 (GitHub mode), the GitHub half of §6.9 (signing in), §6.16 (how a published change reaches the site) and the §11 Phase 3 entry: "an editor with a GitHub account can edit and publish, with an image, from a deployed static site." Two calls are already made (2026-10-19): the cloud will run a free relay, and in GitHub mode the site's build is the last check for custom Markdoc validators. Nothing here touches the cloud, and GitHub mode is free (§4).

**What was found first.** In the code:
- **The storage interface was built for this.** A file's version is its git blob SHA in every mode, a `ChangeSet` is applied whole or not at all, a stale `expectedVersion` is a conflict, and `runStorageContract` is the suite every adapter must pass.
- **The dev API is a thin shell over core.** `ContentService`, `PageService` and `MediaService` do the work, over a storage adapter. GitHub mode can run the same services in the browser over a GitHub adapter, so every screen, check and splice stays the same code. Only five inputs are Node-only today: the collections' Zod schemas, the real Markdoc config, declared MDX props, function-form URLs and the site's static routes.
- **The studio already ships `vesper.config.ts` to the browser** (custom widgets, MDX props), so function-form URLs and MDX props are available there. Static routes can be written into the studio at build.
- **Two things would be slow over the API.** `MediaService.list` reads every media file to hash it, which would download every image, and the studio's `fileUrl()` is synchronous, while a private repo's `src/assets` image has no URL a browser can load without a token.

From GitHub's docs and changelog, checked on 2026-10-19 (sources in DECISIONS.md once confirmed):
- **CORS.** `api.github.com` (REST and GraphQL) answers cross-origin requests with an `Authorization` header from any origin. `github.com/login/oauth/access_token` and the device-flow endpoints don't, so **a relay is needed for any sign-in.**
- **PKCE** (S256) works for OAuth Apps and GitHub Apps since July 2025, but the token endpoint **still requires `client_secret`** for the web flow, so **the relay must hold the secret**.
- **An OAuth App can't be limited to one repository.** Writing to a private repo needs the `repo` scope, which reaches every private repo the editor can reach. New organizations also block OAuth Apps until an owner approves them, which colleges will hit.
- **A GitHub App's user token reaches only the repositories the app is installed on, intersected with the editor's own access.** It needs only Contents (read and write) and Metadata (read), and no webhook or server beyond the relay. Tokens last 8 hours; refresh tokens last 6 months, rotate, and need the secret. An app can list 10 callback URLs.
- **Commits.** The Git Data API (blobs, tree, commit, then a ref update with `force: false`) refuses a ref update that isn't a fast-forward, so a race is caught. Text can go inline in the tree; each binary needs its own blob request. `createCommitOnBranch` (GraphQL) is one request with a true compare-and-swap and Verified commits, but its practical request limit is about 16 MB of base64, and a 20 MB upload is about 27 MB.
- **Reading.** One recursive tree call lists every path and blob SHA (up to 100,000 entries). Batched GraphQL `object(expression:)` queries read many text files in one request. `raw.githubusercontent.com` can't be read from a browser for a private repo; the Contents API's raw media type can.
- **Limits.** 5,000 REST requests an hour per editor, and content-creating requests are capped at 80 a minute and 500 an hour.
- **Hosts.** A commit through the API is a push: GitHub Actions and git-connected hosts build on it. But on private repos **Vercel builds only for commit authors on the team, and Netlify holds unknown authors for approval**, and in GitHub mode each editor is the author. No such rule was found for Cloudflare Pages.
- Decap, Sveltia and Keystatic do much the same. Sveltia is closest to this design: browser-only, with a one-file Worker relay holding an OAuth App's secret.

### How it works

**Turning it on.**
- `vesper({ github: { relay: 'https://vesper-auth.example.workers.dev' } })` in `astro.config`, plus optional `repo: 'owner/name'`, `branch` and `apiUrl` (GitHub Enterprise Server, and the tests' fake GitHub).
- Without `repo`, the build reads it from git: `origin`'s URL, the default branch, and the site's folder inside the repository (`git rev-parse --show-prefix`), so a monorepo's site saves to the right paths. With none, the build says so in one line and `/admin` is the "Editing isn't available here yet" screen it is today.
- `astro dev` stays local mode. GitHub mode runs in built sites only, which is also how the tests run it.

**Signing in** (a top-level redirect, no popup, no third-party cookies, as D14 does for the cloud):
1. "Sign in with GitHub" saves a random `state` and a PKCE verifier in `sessionStorage` and goes to the relay's `/authorize`, with the site's origin, the state and the code challenge.
2. The relay checks the origin against its allowlist and sends the browser to GitHub with its own client ID and its `/callback`.
3. GitHub returns to the relay, which sends the browser back to `<site>/admin/?github=<code>&state=…`. The code is useless without the verifier, which never left the studio's tab.
4. The studio checks the state and posts the code and verifier to the relay's `/token`. The relay adds the secret, asks GitHub, and answers with the token (CORS for allowlisted origins only). The studio removes the code from the address with `history.replaceState`.
5. The studio reads the repository's permissions. An editor who can't push sees "Your GitHub account can't change this site. Ask its owner to add you." and Sign out.

**Reading.** `GitHubStorage` implements `StorageAdapter`:
- `head()` is the branch's commit SHA. `list()` comes from one recursive tree at that head.
- `read()` goes through an IndexedDB cache keyed by blob SHA. A SHA always means the same bytes, so the cache never goes stale, and only changed files are fetched again. Misses are fetched in batches, text through GraphQL and binaries one at a time through the Contents API's raw media type.
- A tree GitHub truncates (over 100,000 entries) falls back to one tree per collection folder.

**Saving.** `commit(changeSet)` is one commit on the branch, by the Git Data API (spec §6.8):
- It reads the head's tree and checks every `expectedVersion` against it. A file someone else changed is a conflict, reported as local mode reports it.
- Binaries go up as blobs, one request each. Text goes inline in a tree built on the head's tree. Then it makes the commit and moves the branch with `force: false`.
- If the branch moved in between (GitHub answers 422), it reads the new head, checks the same files again and retries once if none of them changed.
- The editor is the commit's author. The message is plain, from the change set's summary ("Update “Harbor at dawn” in Blog posts"), with its trailers.
- A branch rule that refuses the push (pull requests required, signed commits required, status checks) is said plainly: "This site's GitHub settings don't allow publishing straight to main." Pull-request mode is Phase 9 (§13.5).

## Phase 2.9: Site search (design)

Scope is spec §6.19 (D23) and the §11 Phase 2.9 entry. Search is free and lives in the open-source integration (D23, §13.4). Nothing here touches the cloud. Search insights stays on the do-not-build list.

**What was found first.** Pagefind 1.5.2 (the current release, MIT) was installed in a scratch folder, not the repo, and measured on a copy of the playground's static build (33 pages):
- **The Node API works as the spec describes:** `createIndex()`, then `addHTMLFile({ url, content })` for each page, then `writeFiles({ outputPath })`. With the service start, 33 pages take 0.1–0.2 s. `addHTMLFile` takes the HTML as a string, so the annotated copy never touches disk and the deployed file is never written.
- **`data-pagefind-body` drops pages silently, as documented.** With the attribute on one page, the index held 1 page of 33. `addHTMLFile` returned no error or warning for the 32 it would leave out, so Vesper has to look for the attribute itself to warn.
- **Without that attribute, Pagefind indexes all of `<body>` except `<nav>` and `<footer>`.** The header stays in, so every playground result began "Skip to contentVesper playground…". With `data-pagefind-body` on `<main>`, results hold only the page's content.
- **`<meta>` tags in the head can carry the annotations.** `<meta data-pagefind-meta="title[content]" content="…">` sets a result's title, date or image. The same form with `data-pagefind-filter` and `data-pagefind-sort` sets filters and sort keys. Values may contain commas, and two tags with one filter name give two values. Without them, Pagefind uses the first `<h1>` as the title and the page's first `<img>` as the image, which gave the blog listing one post's picture.
- **Headings already outrank body text.** For "harbor", the post titled "Harbor at dawn" scored 15.4 and the next page 5.3. When the title is the page's `<h1>` inside `<main>`, no extra weighting is needed.
- **Languages need nothing from Vesper.** Pagefind writes one index per `<html lang>`: a docs page set to `es` got its own `es` index and wasm. The browser loads the index for the page's language.
- **Sorting drops pages that lack the sort key.** "campus" found 10 pages by relevance and 5 sorted by date: the 5 pages without a date were left out.
- **The WebAssembly needs no MIME type.** Pagefind's files are `wasm.<lang>.pagefind`, `*.pf_meta`, `*.pf_index`, `*.pf_fragment` and `*.pf_filter`. Its script fetches each as bytes, gunzips it itself and instantiates the wasm from memory, so `WebAssembly.instantiateStreaming`, the only path that needs `application/wasm`, is never taken. `scripts/static-server.mjs` serves these files as `application/octet-stream`, as a host with no MIME settings would, and search worked. No `.wasm` file exists to map.
- **Size.** The index of 33 pages is 22 KB; the rest is fixed cost. From a page using Component UI, a first query loaded 389 KB uncompressed (about 155 KB with gzip):
  - 219 KB of Component UI's JS and CSS, on every page load, before anyone searches;
  - then `pagefind.js` (46 KB), its worker (41 KB), the English wasm (72 KB, already gzipped), an 8 KB index chunk and the fragments.
  - Without Component UI, Pagefind's part of a first query is about 170 KB uncompressed.
- **Install size.** `pagefind` is 37 KB, plus a 58 MB binary for the build machine's platform (an optional dependency such as `@pagefind/linux-x64`). `writeFiles` also writes Pagefind's three bundled UIs and its highlighter into the output: about 420 KB that a site using none of them doesn't need.

### What gets indexed

Indexing lives in `packages/astro/src/integration/search.ts` and runs in `astro:build:done`, after the accessibility check.

**Pages.** The indexer walks the same HTML files as the build's accessibility check (`builtPages`). It leaves out:
- Astro's redirect pages, `/admin`, `404.html` and Vesper's `/search` page;
- pages with `<meta name="robots" content="noindex">` (a default below);
- URL patterns in `vesper({ search: { exclude: ['/tags/**'] } })`;
- entry pages, traced through the collection's `url` exactly as the accessibility report does (`PageService.pageEntries`, `urlKey`), when:
  - the collection has `search: false`; or
  - the entry is hidden from search; or
  - the entry is outside its publish window. Until Phase 4.5 filters the build itself, this check keeps scheduled and unpublished entries out (a call below).

Static pages in `src/pages` are indexed (spec §6.19).

**When indexing is skipped.** With no built page using `<Search>` (the component renders a `data-vesper-search` marker), the integration skips indexing and logs one line saying so. `vesper({ search: false })` turns search off.

**The annotated copy.** It's what Vesper hands `addHTMLFile`; the file in `dist/` is never written.
- **Content area.**
  - If no page in the build has `data-pagefind-body`, the copy adds it to each page's first `<main>`, or to `<body>` for a page with no `<main>`. One build note lists those pages.
  - If any page has the attribute, the site's own markup rules. The build then warns when that leaves out pages Vesper would otherwise index: "Search: /landing/ uses data-pagefind-body, so Pagefind leaves out the 31 pages without it: /about/, /blog/welcome/ and 29 more. Add data-pagefind-body to their layout, or leave pages out with search: { exclude }."
  - `data-pagefind-ignore` is Pagefind's and works as documented.
- **Meta, in `<head>`.**
  - `title` is the entry's title (`titleOf`); a static page gets Pagefind's own default, its first `<h1>`.
  - `date` is the entry's first `search.sort` field, or else its first date field. It's formatted in the page's language and the site's `timeZone`.
  - `image` is the search thumbnail, with `image_alt` empty. The UI renders thumbnails with `alt=""`.
- **Filters.**
  - `Section` is always set to the collection's label.
  - Then each field in `search.filters[collection]`:
    - strings and lists of strings as they are;
    - `fields.select` values by their labels;
    - references by the referenced entry's title.
  - Other kinds warn once and are skipped.
- **Sort keys.** Each field in `search.sort[collection]` becomes a key of the same name, written as an ISO date and time so the keys sort correctly as text.
- **Thumbnails.**
  - Each comes from the entry's first `fields.image()` value, cut with the **square** crop through `cropForRatio` and `pixelRect`: the stored crop when there is one, otherwise the focal crop. That's how focal points carry through.
  - Sharp writes it as a 128px WebP (shown at 64px) to `dist/_vesper/search/images/<hash>.webp`. The hash covers the source file and the rectangle, so unchanged images keep their names across builds.
  - Without Sharp there are no thumbnails, and one log line says why.

**Output.**
- `writeFiles` writes into `dist/_vesper/search/`. Pagefind's bundled UIs and highlighter are then removed.
- The build logs one line, for example: "Search: indexed 31 pages in 2 languages, 48 KB of index. A first search loads 214 KB."
- It warns above the 300 KB first-query budget. That's measured as the uncompressed bytes of the script, the worker, the largest language's wasm, its meta and its largest index chunk.

### `<Search>` and the pages around it

**`<Search>`** ships in `@vesper/astro/components` as source `.astro`, like `<Img>`. It comes with a small, framework-free script (the design for call 1a).
- **`<Search />`** renders a "Search" button.
  - Without JavaScript, the button is a link to `/search/`.
  - With JavaScript, it opens a native `<dialog>` with `showModal()`.
- **The dialog** holds, in order: a visible close button "Close"; a labelled `type="search"` field ("Search this site"); the filters; and the results.
  - Its polite live region sits **inside the dialog**. It says "12 results for “nursing”" or "No results for “nursing”" once typing pauses, never on every keystroke.
  - Escape closes it from anywhere and returns focus to the button; the query is kept for the next opening. There are no keyboard traps.
- **Results** are a `<ul>` of links: the title as the link's text, a `<time>` with the date, the excerpt with `<mark>`, and the thumbnail with `alt=""`.
  - The first 10 results are real list items. "Show more results" adds 10 more and moves focus to the first new one; nothing is `aria-hidden`.
  - ArrowDown from the field moves to the first result, and Tab goes through the results in order.
  - `mark` keeps the system's Mark colours in forced colours.
- **Filters** are a `<fieldset>` with a legend per filter ("Section", "Tags"). They're checkboxes whose labels hold their counts ("Events (5)"), and each change re-announces the count.
- **Sort** is a `<select>` named "Sort", offered once a section with a sort field is chosen (a default below).
- **`<Search variant="inline" />`** puts the same field, filters and results in the page, with no dialog.
- **Look.** The UI inherits the site's font and colours (`font: inherit`, `currentColor` borders, `Canvas` and `CanvasText` fallbacks, so dark sites stay dark). A few custom properties cover the rest: `--vesper-search-accent`, `-surface`, `-border` and `-radius`. The README shows the lines that theme it.
- **Loading.** Pagefind's `pagefind.js` loads only when the dialog first opens or the inline field first gets focus, from `<base>_vesper/search/`.
- **In `astro dev`**, Vesper's dev middleware serves the last build's `dist/_vesper/search/`. With no build yet, the dialog says "Search works after `astro build`."
- **Strings.** English is built in. Other languages come from `vesper({ search: { strings: { fr: {…} } } })`, keyed by the page's `lang` and seeded from Pagefind's MIT-licensed translations where the messages match, with credit.

**`/search`** is injected with `injectRoute` and prerendered, respecting `base`, `trailingSlash` and `build.format`. It holds `<Search variant="inline" />`, reads `?q=` and runs the query on load. A site's own `src/pages/search.astro` wins (call 7).

**`opensearch.xml`** goes at the site root. Its template URL must be absolute, so it needs Astro's `site`; without one it's skipped with one log line. `<SearchHead />` goes in the layout's `<head>` and emits the `<link rel="search">`, because that link type isn't allowed in `<body>`.

**Without JavaScript,** `/search` is a plain form that submits `?q=` to itself, and a `<noscript>` explains that search needs JavaScript (call 8). `search: { noJsFallback: 'duckduckgo' }` makes the form's action DuckDuckGo, with `sites=<host>` (which needs `site`). The script takes the form over when it runs, so only visitors without JavaScript send their queries to DuckDuckGo.

**Static hosts (D16).**
- The static e2e runs search against `scripts/static-server.mjs`, which already serves `.pagefind` files as `application/octet-stream`.
- `static-server.test.mjs` pins that.
- No `.htaccess` line is added, because Pagefind needs no MIME type. DECISIONS.md records why, so nobody adds one later.

### The calls (confirmed 2026-10-19)

Jeremy confirmed every recommendation on 2026-10-19: 1a to 10a, and the smaller defaults.

1. **The search UI (the audit's result).**
   - (a) Vesper's own small script on Pagefind's JS API, recommended: a native `<dialog>`, a list of links, fieldsets and a live region inside the dialog. It would be about 8 KB gzipped (an estimate), and every behaviour is tested here. A first query would be about 200 KB uncompressed, 170 KB of it Pagefind's.
   - (b) The ui kit's React Aria Dialog, ComboBox and ListBox, compiled into a bundle loaded on first open. That brings the studio's tested behaviour, but puts React on public pages. Measured, React 19.3 alone is 75 KB gzipped and 149 KB with those components, about 600 KB uncompressed. That alone breaks the 300 KB budget on a host without compression.
   - (c) Component UI, themed, with Vesper's workarounds for findings 1 to 3 and custom templates for 7 and 8. It's the least code now, but the fixes for 1 and 2 reach into Pagefind's internals and could break with any release.
2. **A list of links, or a combobox.** The spec asks for "results as a real list of links", and for the fallback "the combobox/listbox pattern". The two conflict, because a listbox's options can't be links.
   - (a) A labelled search field and a list of links, with ArrowDown from the field to the first result. Recommended.
   - (b) A combobox whose options are links with `role="option"`, as Pagefind's searchbox does. Screen readers then don't treat them as links, so they leave the links list and lose "open in new tab".
3. **The "/" shortcut.** WCAG 2.1.4 (A) requires that a visitor can turn a one-character shortcut off, remap it, or have it work only on focus. A setting the site's developer controls doesn't count.
   - (a) Ctrl/⌘+K, recommended. It has a modifier, so 2.1.4 doesn't apply. It's in the button's `aria-keyshortcuts` and description, and `<Search shortcut={false}>` turns it off. No "/" in v1.
   - (b) "/" as the spec says, plus a "Use / to open search" switch in the dialog, remembered in the visitor's browser.
   - (c) Both, with (b)'s switch for "/".
4. **Where "Hide from site search" is stored.**
   - (a) In a field the schema declares, recommended: `fields.hideFromSearch()` (a boolean, default false), or a boolean SEO field named `noindex` (at the top level or under `seo`), found by name. Astro validates it, and the site's layout can use the same value for `<meta name="robots">`. With neither field, there's no switch.
   - (b) In a key Vesper writes into the frontmatter without a schema field. That needs no setup, but Zod strips unknown keys, so the site's code never sees it, and `.strict()` schemas fail the build.
   - (c) In a list of hidden entries in a file of Vesper's. That needs no schema change, but it's a second place to keep in step when entries move.
5. **Scheduled entries before Phase 4.5.** Builds still produce them today: the playground's `harvest-concert` publishes on 31 October and showed up in the probe's results.
   - (a) The indexer leaves out entries outside their publish window, using a check in core that 4.5's filtering will reuse. Recommended.
   - (b) Bring 4.5's build-time filtering forward into this phase.
   - (c) Move "scheduled entries never appear" to 4.5's criteria.
6. **`data-pagefind-body` on some pages.**
   - (a) Respect Pagefind's rule, and warn with the pages it leaves out. Recommended: it's Pagefind's documented behaviour, and some sites use it to choose their pages.
   - (b) Use the site's attribute where a page has it and `<main>` everywhere else, so no page drops. That's friendlier, but it differs from Pagefind's docs.
7. **The `/search` page.**
   - (a) Inject a plain page unless the site has `src/pages/search.astro`, which then wins. Recommended; the playground has its own page.
   - (b) Inject it inside a layout named in the config. The layout would have to take a `title` prop and a slot.
   - (c) Never inject it, and have the docs show the five-line page.
8. **Where `/search` sends visitors without JavaScript.** Generating a sitemap is on the do-not-build list.
   - (a) "Search needs JavaScript." with a link to the home page, or to a page the site names (`search: { noJsLink: '/site-map/' }`), plus `sitemap-index.xml` when the build has one. Recommended.
   - (b) Only the message, plus the DuckDuckGo option.
9. **Pagefind's install size:** a 58 MB binary for the build machine's platform.
   - (a) A dependency of `@vesper/astro`, as D23's "on by default" implies. Recommended; Starlight does the same.
   - (b) An optional peer, which the build asks for when a page uses `<Search>`.
10. **The first-query budget.**
    - (a) Count uncompressed bytes, what a host without compression sends, and warn above 300 KB. Recommended; call 1a comes to about 200 KB.
    - (b) Count gzip-estimated bytes.

**Smaller defaults, built as written unless you say otherwise:**
- The collection filter is called "Section" ("Blog posts", "Events", "Pages", "Docs"). Static pages have no section.
- Sorting is offered only once a section with a sort field is chosen, because Pagefind drops pages without the key.

- Tier: nothing is unclear. §13.4 lists site search as free, and search insights stays on the do-not-build list.

**Not in this phase:** search insights (do-not-build); search in the studio's ⌘K palette (§10.3); ranking controls beyond headings (`data-pagefind-weight` is Pagefind's and still works); custom result templates; anything in the cloud.

## Phase 2.8: Accessibility checks (design)

Scope is spec §6.18 layers 1 and 2 and the §11 Phase 2.8 entry. Layer 3 (cloud history, full rendered scans, exports, the agency view) is paid and belongs to Phase 8.5: nothing of it is built here. Both layers report problems; neither claims compliance, and nothing is injected into the site (D19).

**What was found first** (measured on the playground's static build, 38 HTML files, before writing any code):
- axe-core 4.14 runs in **jsdom** 30 and **happy-dom** 21. Over the same 60 structure rules (below), both gave exactly the violations real Chromium gives on every one of the 38 pages. jsdom needs one shim: it has no `document.elementFromPoint`, and without it the page-level rules (`landmark-one-main`, `page-has-heading-one`) error out and land in "incomplete". **linkedom** 0.18 can't run axe at all (no `screen`, no `getComputedStyle`), not without shimming half a browser.
- Time per page: jsdom about 100 ms (construction 21 ms, loading axe 14 ms with one compiled `vm.Script`, the run 66 ms), happy-dom about 60 ms. Loading the module once: jsdom 2.7 s, happy-dom 1.1 s. Installed: jsdom 25 MB in 30 packages, happy-dom 20 MB in 7, axe-core 3.4 MB.
- jsdom with `runScripts: 'outside-only'` never runs the page's own scripts while still letting axe in. happy-dom needs JavaScript evaluation on to load axe the same way, which runs the page's inline scripts too.
- Astro's static redirect pages (a meta refresh, no `lang`, no `main`) fail `html-has-lang`, `landmark-one-main`, `page-has-heading-one` and `region`. That's Astro's template, not the site's content, so the build check skips them, as the e2e gate already does. The `/admin` shell fails the same landmark rules before its script runs; the studio has its own axe checks in e2e, so it's skipped too.
- Of the fixture page's mistakes, axe sees only `empty-heading` and `heading-order` at build (plus `color-contrast` in a real browser, which layer 2 doesn't check). The rest are content problems only the studio can see, which is why layer 1 exists.
- PDF.js 6.4 (`pdfjs-dist`, Apache-2.0) reads the fixture PDF in 76 ms: `getMarkInfo()` is null (untagged), `getMetadata()` has no `Title` and `Language: null`. Its modern build needs `Uint8Array.prototype.toHex` (Chrome 140, Firefox 133, Safari 18.2 and later); the legacy build doesn't. Minified, the legacy build is 524 KB plus a 1,321 KB worker.
- Markdoc with `allowHTML` gives inline and block HTML as `html_inline` / `html_block` nodes with line ranges and no content, so HTML is read from those lines of the source.

**Rules** (`packages/core/src/a11y/`, no dependencies, so the studio, the dev API and the cloud can share them). Each rule has an ID, a plain-language message, one sentence on why it matters, and a docs slug for the link the docs will hold (spec §6.18: "a link to a short explanation in the docs"). The spec's twelve rows become seventeen IDs, so `blockPublishOn` can name exactly what it blocks:

| ID | Fires on | Message (example) | Shown beside |
|---|---|---|---|
| `missing-alt` | An image field with no alt text and not `decorative`; an HTML or JSX `<img>` with no `alt` | "Describe this image, or mark it decorative." | The image field (Go to: its alt text), or the body |
| `alt-file-name` | Alt text that is a file name (`IMG_2041.jpg`, `DSC0042`, `photo-1.png`) | "Alt text looks like a file name." | Same |
| `alt-redundant` | Alt text starting "image of", "picture of", "photo of", "graphic of" | "Leave out “Image of”: screen readers already say it’s an image." | Same |
| `alt-too-long` | Alt text over 150 characters | "This alt text is 214 characters long. Keep it under 150 and put the rest in the text." | Same |
| `heading-skip` | A heading more than one level below the previous one, or a first heading below the start level | "Heading jumps from level 2 to level 4." | The body |
| `heading-extra-top` | A heading above the collection's start level (an `h1` when the title is the page's `h1`), or a second `h1` when the start is 1 | "The title is already the page’s main heading. Use level 2 here." | The body |
| `heading-empty` | A heading with no text | "This heading is empty." | The body |
| `link-vague` | Link text such as "click here", "here", "read more", "more", "learn more", "this link", or the bare address | "Link text should say where it goes." | The body, a Markdown field |
| `link-new-window` | `target="_blank"` with no "new tab" or "new window" in the link's text, `aria-label` or `title` | "Tell readers this opens in a new tab." | Same |
| `table-header` | An HTML or JSX table with no `<th>` (Markdown and Markdoc tables always have a header row in their syntax) | "Add a header row so screen readers can announce columns." | The body |
| `color-contrast` | A `fields.color({ contrast: 'text' })` value under 4.5:1 (`'large-text'` and `'graphic'`: 3:1) against any background the site declares | "Contrast 2.3:1 against Page, light is below 4.5:1." | The colour field |
| `tag-name-empty` | A Markdoc tag or declared MDX component whose required name attribute (`title`, `alt`, `label`, `aria-label`) is empty text. A missing one is already a validation error | "YouTube video needs a title." | The body |
| `fake-list` | A paragraph with two or more lines that start like list items (`-`, `*`, `•`, `1.`, `1)`, escaped or not) | "This looks like a list. Format it as one." | The body, a Markdown field |
| `pdf-untagged` | A PDF in a file field, or linked from the body, with no structure tags (`MarkInfo` / `StructTreeRoot`) | "This PDF isn’t tagged, so screen readers can’t read its structure. Consider an HTML page instead, or tag the PDF." | The file field, or the body |
| `pdf-no-title` | Such a PDF with no document title (Info or XMP) | "This PDF has no title, so screen readers announce its file name instead." | Same |
| `pdf-no-language` | Such a PDF with no language set | "This PDF doesn’t say what language it’s in." | Same |
| `video-captions` | A tag or component whose schema has a `captions` attribute, used without it or with it off | "Confirm this video has captions." | The body |

- Body checks read each format with the parser the site renders with: micromark (GFM, plus MDX) for `.md` and `.mdx`, Markdoc with Astro's tokenizer options for `.mdoc`. HTML (and lowercase JSX in MDX) is read with a small tag scanner over the block's own text. Each note carries the body offsets and line of what it's about, and a short subject ("Image “IMG_2041.jpg”", "Heading “A heading that skips level 3”").
- `fields.markdown()` values get the image, link and fake-list rules, not the heading rules.
- PDFs: core only turns facts (`tagged`, `title`, `language`) into notes. Reading the file is the studio's job, with PDF.js, loaded the first time an entry has a PDF to check, and its result cached per file version.
- Contrast is the WCAG 2.1 relative-luminance ratio, rounded down to one decimal for the message, so a value never reads as passing when it doesn't.

**Settings** (spec §6.18 names `a11y.blockPublishOn` a site setting):
- `vesper.config.ts`: `a11y: { blockPublishOn?: RuleId[]; backgrounds?: Record<string, string> }`. Unknown rule IDs warn when the config loads. With no backgrounds declared, contrast isn't checked, and the manifest warns once if a colour field asks for it.
- `collections.<name>.headingStart`: the level the body's top headings should have, 2 by default (the layout's `<h1>` is usually the title).
- `fields.color({ contrast: 'text' | 'large-text' | 'graphic' })` in `@vesper/astro/fields`; raw Zod: `.meta({ widget: 'color', widgetOptions: { contrast: 'text' } })`.
- The manifest gains `site.a11y` (`blockPublishOn`, `backgrounds`) and `presentation.headingStart`.

**Studio** (`packages/admin`):
- `a11y/useNotes.ts`: runs the core checks on the entry's values and body a moment after typing stops (the same 300 ms as body validation), then the PDF checks as their files load. Body checks load with the body checks' chunk; PDF.js loads on first use (`a11y/pdf.ts`, `pdfjs-dist/legacy`, worker through a Vite `?url` import, as the map's worker is).
- Beside each field: notes go under the field's help and error text, as "Accessibility note: …" in body text with a hairline warning border on the left, and are joined into the control's `aria-describedby`. A note inside a field (an image's alt text) shows under that field; Go to focuses the alt text.
- Beside the body: a list "Accessibility notes in the body" under the editor's help line. Each item names its subject and has a "Show" button that puts the cursor on that block in the writing view (or selects its text in the source view) and scrolls it into view.

## Phase 2.7: Focal points, crops and `<Img>` (design)

Scope is spec §6.6.2 to §6.6.5 and the §11 Phase 2.7 entry. Body images keep Astro's own processing and get no focal point or crops in v1 (§6.6.5).

**What was found first** (DECISIONS.md, "Astro hands `position` to Sharp unchanged"), measured with real builds on Astro 7.4.0 and the fixture's 6.4.8, which agree:
- `position` and `fit` reach Sharp untouched, and Sharp takes only its own keywords. `"62% 35%"` and CSS-order `"top right"` fail the build (and are a 500 from `/_image` in dev). With `layout`, every `srcset` width sends `position` to Sharp.
- Astro's CSS for `data-astro-image-pos` covers keyword pairs only. An inline `object-position` style passes through and wins.
- A transform key Astro doesn't know (`crop`) reaches the service but isn't hashed, so two crops shared one file, and it leaked into the `<img>` as an attribute.
- Astro 7.4 can configure separate `build` and `runtime` services; `imageConfig.service` in `astro:assets` is the one for the current environment, on both majors.
- Sharp's `.rotate().extract()` rotates first, so a crop measured on the upright image (what browsers show) is cut correctly from an EXIF-rotated file.

**Geometry** (`packages/core/src/images/`, exported as `@vesper/core/images` and from the main entry; no dependencies, so the studio, the build and `<Img>` share it):
- Types: `FocalPoint { x, y }` and `CropRect { x, y, w, h }`, both 0–1 from the top left (§6.6.2); `ImageSize { width, height }`.
- `siteRatios(declared)`: the declared ratios plus the built-in `og` (1.91:1) unless the site redefines it. `ratioLabel(1.777…)` is "16:9" (the nearest fraction with a denominator up to 20, else "1.91:1").
- `focalCrop(size, ratio, focus)`: the largest rectangle of that ratio, centred on the focus (the centre when there's none), kept inside the image.
- `cropForRatio(value, name, ratio, size)` → `{ rect, custom }`: the stored crop for that ratio name, else the focal crop. A stored crop whose pixel shape no longer matches its ratio (the image was replaced) is trimmed to the ratio around its own centre.
- `pixelRect(rect, size)`: whole pixels, clamped, the one rounding rule the wrapper and the studio both use.
- `moveRect`, `scaleRect` (fixed ratio, around the centre or a corner), `clampRect`, `focusWithin(rect, focus)`, `objectPosition(focus)` ("62% 35%"), `sharpAnchor(rect)` (the nearest of Sharp's nine anchors, and the rectangle Sharp would cut there), `roundFocus` (two decimals: the 1% steps the control makes) and `roundRect` (four decimals).
- `imageValueOf(value)`: reads `focus` and `crops` defensively from an entry's value, ignoring anything malformed.

**Schema and config** (`packages/astro`, `packages/core`):
- `fields.image(image, { ratios? })` in `@vesper/astro/fields`, typed so `src` keeps Astro's `ImageMetadata`:
  `z.object({ src: image(), alt: z.string(), decorative: z.boolean().optional(), focus: z.object({ x, y }).optional(), crops: z.record(z.string(), rect).optional() })`, with the playground's existing refinement (alt text, or decorative with `alt: ""`), rectangles that stay inside the image, and `.meta({ widget: 'image', widgetOptions: { ratios } })`. The README shows the raw Zod.
- `vesper.config.ts` `images: { ratios, maxUploadEdge }` is checked when it loads: ratio names are words, values are positive numbers, `maxUploadEdge` is a whole number of pixels.
- The manifest gains `site.images` (`ratios` with `og` included, and `maxUploadEdge` when set), and a warning when an image field lists a ratio the site doesn't declare. The studio's upload hygiene starts using `maxUploadEdge` (it was fixed at 3000).

**The crop step** (`@vesper/astro/image-service`, `src/images/service.ts`): Astro's Sharp service with one more transform option, `crop` (a normalized rectangle):
- `propertiesToHash` adds `crop` to Astro's own list, so each crop gets its own file.
- `validateOptions` checks the rectangle (a plain-language error names the image) and drops it for SVG and GIF sources, which Sharp passes through or animates.
- `getURL` and `parseURL` carry it as `crop=x,y,w,h` on `/_image`, so dev crops too; `getHTMLAttributes` keeps it out of the page.
- `transform` cuts the rectangle out of the upright image (`rotate().extract()`), as a lossless PNG, then hands that to Astro's own Sharp transform for resizing and formats. Without `crop` it's Astro's transform, untouched.
- The integration registers it in `astro:config:setup` only where the site uses Astro's Sharp service (the flat form, or either target of Astro 7.4's `{ build, runtime }`), keeping the service's `config`. `vesper({ imageService: false })` turns it off. The build log says it's on and how to turn it off.
- `sharp` becomes an optional peer dependency of `@vesper/astro`: the wrapper loads the copy Astro already depends on, and a strict installer (pnpm) has to let it resolve.

**`<Img>`** (`@vesper/astro/components`: `components/Img.astro` and `getImg()`, shipped as source like the `/admin` page; the planning is `src/images/plan.ts`, exported as `@vesper/astro/images` so it's unit-tested and Node-loadable):
- `virtual:vesper/images` gives the site's ratios. Which service is active comes from `imageConfig.service.entrypoint`: Vesper's wrapper, Astro's Sharp, or anything else.
- `ratio` (a declared name or a number), or `width` and `height` together (a ratio of their own): the crop from `cropForRatio`. With the wrapper, Astro's `<Image>` (`<Picture>` when `formats` is given) gets the exact width and height plus `crop`. Without it, the same width and height (Astro's own server crop), `position` set to the nearest Sharp anchor when the service is Astro's Sharp, and nothing for other services. Either way the focal point, relative to what was cut, goes into `style` as `object-position`.
- Widths are capped at the crop's own pixel width, as Astro caps them at the original's, so a 720-pixel crop is never labelled 1440w. With a `layout` and no `widths`, the widths are worked out the way Astro does from its breakpoints, against the crop's width.
- No ratio and no fixed size (fluid layouts): the original, no server crop, the focal point as `object-position`.
- `art={{ base: 'square', '(min-width: 48rem)': 'wide' }}`: a `<picture>` built with `getImage()`. For each breakpoint in the order given, one `<source media>` per format (`formats`, default WebP) with that ratio's own crop, `srcset`, `sizes`, and its own `width` and `height`; then the base ratio's sources without `media`, then the `<img>` in the fallback format (the original's for JPEG and GIF, else PNG, as Astro's `<Picture>` chooses).
- Always: `alt` from the field, `alt=""` when `decorative`. Every other Astro prop passes through. A ratio name the site doesn't declare fails the build with the declared names listed.
- `getImg(props)`: the same crop for one image, returning Astro's `getImage()` result (for `og:image` and the like).

**Studio** (`packages/admin`, `packages/ui`):
- The image field shows its image, the alt text and one more control: a "Focal point & crops" disclosure (the kit's `Disclosure`), only for fields that store `focus` or `crops`, and only once an image is chosen (§6.6.4 "calm by default"). A plain `image()` field never shows it.
- Focal point (`widgets/focal-point.tsx`): the image is one button, named "Focal point" and described by its position ("62% across, 35% down") and how to move it. A click or tap sets the point, and the marker can be dragged. With focus on it, the arrow keys move the point 1%, Shift+arrows 10%. Beside it, "Across (%)" and "Down (%)" number fields (0–100) set it without seeing or pointing. Each keyboard or pointer move is announced in a polite live region: "Focal point 62% across, 35% down." "Use the center" removes `focus`.
- Crop previews (`widgets/crops.tsx`): a strip of small figures, one per ratio the field lists (or every site ratio), each the image cropped by CSS from the same `cropForRatio`, captioned with its name and ratio ("Wide · 16:9") and "Custom crop" in text when overridden. They follow the focal point live. Each has an "Adjust crop" button (named "Adjust crop for Wide").
- The crop dialog (the kit's `Dialog`, in a new wide size): the image with a fixed-ratio crop box over it, and the area outside dimmed. Drag the box to move it, drag a corner to resize it. The box is one focusable element (`role="application"`, named "Crop box for Wide (16:9)" and described by its keys), so screen readers pass the arrow keys through: arrows move it 1%, Shift+arrows resize it (Shift+→ and Shift+↓ grow, Shift+← and Shift+↑ shrink, around its centre), Enter applies, Escape cancels. Moves are announced: "Crop 40% from the left, 10% from the top, 45% of the width." Buttons: "Reset to focal point" (only when the ratio has a custom crop; it removes the override and closes), "Cancel", and "Apply crop" (the dialog's one primary). Applying an untouched box over a ratio with no override writes nothing.
- Values: focal points with two decimals, crops with four. Removing the last crop removes `crops`. Nothing but the entry is written: the image file is never touched.

**Where each feature lives in the UI** (§10.4): inside the image field, behind the "Focal point & crops" disclosure. The crop tools hide behind each preview's "Adjust crop" button, in a dialog. No new screens, panels or navigation.

## Phase 2.6: URLs, hierarchy and redirects (design)

Scope is spec §6.15 and the §11 Phase 2.6 entry. Confirmed before starting (DECISIONS.md, 2026-10-18): `vesper.redirects.yaml` sits at the site root, and `maxDepth` is optional with no default.

**What was found first** (measured on Astro 7.4, React Aria Components 1.22 and the playground):
- Astro's glob loader drops a trailing `/index` from IDs but keeps a top-level `index.md` as `index`. Vesper's `defaultEntryId` already matches, so `:path` only has to turn `index` into the root.
- `astro:routes:resolved` (Astro 6 and 7) gives every route with its `pattern`, `patternRegex`, `params`, `type`, `origin` and `entrypoint`, before the build starts and when dev starts. That's enough for the route check and the static-route collision check.
- Astro's static redirect page is a meta refresh (`redirectTemplate`): no delay for 301, two seconds for 302. On the plain static host, `/old` first gets the host's own slash redirect to `/old/`, then the meta refresh. So redirect targets must be written in the page's canonical form (`/academics/nursing/`), or every redirect gains a second hop.
- The YAML writer appends flow maps shaped like their neighbours and writes new dates date-only, so redirects can go through `writeDataFile`. Inserting into the middle of a scalar sequence (reordering `_order.yaml`) replaced the whole sequence and dropped the file's leading comment: fixed in the writer, not worked around.
- React Aria's `Tree` is a single-column `treegrid` with `aria-level`, `aria-expanded`, arrow keys, Home/End, type-ahead, rows with interactive content, and keyboard-accessible drag and drop. WAI-ARIA's own guidance is a treegrid when rows hold buttons (each page has a "…" menu), so that's what the outline is.
- Vercel reads `vercel.json` before the build runs, so redirects merged into it at build time would never apply. They're merged when the studio writes the redirects file instead.

**URLs** (`packages/core/src/urls/`, exported as `@vesper/core/urls`: no Markdoc, no YAML, small enough for a site's own pages):
- `pattern.ts`:
  - `UrlSettings` (`base`, `trailingSlash`, `buildFormat`, `timeZone`) come from Astro's config and `vesper.config.ts`, into the manifest's `site.urls`.
  - `expandUrlPattern(pattern, { id, data })` handles `:id`, `:path`, `:slug`, `:<field>` and `:<dateField>|yyyy|mm|dd`. Date parts are read in the site's time zone, else UTC, so the studio, dev and build agree.
  - `formatUrl(path, settings)` adds `base` and the trailing slash Astro's settings imply (`always` or `never`; `ignore` follows `build.format`). `urlKey(url, settings)` is the comparable form: no base, query, hash or trailing slash.
  - The function form `url: (entry) => string` runs where vesper.config.ts is loaded (dev API, build, `vesper:content`). In the studio's own bundle it loads lazily, as custom widgets do.
- `tree.ts`: `buildTree(entries, orders)`. Folders are the hierarchy and `foo/index` is foo's section page. A folder without one is still a node (no entry, no URL), so the studio can flag it. Children follow `_order.yaml` first, then unlisted ones by title (`Intl.Collator('en', { numeric: true })`, the same everywhere). Also `childrenOf`, `breadcrumbsOf` and `pathDepth`.
- `redirects.ts`: `cleanRedirects(list, pages)`, run every time the file is written and at every build:
  - loops are removed (self-redirects, cycles, and chains that run into a cycle);
  - chains collapse (A→B→C becomes A→C); the result is temporary if any hop was;
  - a redirect whose `from` is now a real page is dropped, with a warning: the page wins;
  - a repeated `from` keeps the later entry;
  - a `to` that's neither a page, a redirect nor an external URL is flagged (warning), never removed.
- `hosts.ts`: rules per host, as pure functions:
  - `_redirects` for Netlify (forced `301!`) and Cloudflare Pages;
  - `.htaccess` `RedirectMatch` lines between `# BEGIN vesper` / `# END vesper`;
  - nginx `location =` blocks;
  - Vercel `redirects` entries.
  - `mergeMarkedBlock` replaces Vesper's block and leaves the rest of the file alone.
- `csv.ts`: `parseRedirectsCsv(text)`. It reads `from,to[,status]` with or without a header, the WordPress Redirection plugin's export (`source,target,regex,code,…`) and Drupal's Redirect import (`source,destination,…,status_code`). It turns absolute old-site URLs into paths, skips regex rows with a reason, and reports each problem row in words.

**Content operations** (`packages/core/src/studio/`):
- `order.ts`: reads `_order.yaml` and writes it through `writeDataFile`, so comments survive.
- `links.ts`: `rewriteLinks(file, moves)` finds links to the old URLs and changes only those bytes:
  - Markdown links, images and reference definitions (micromark positions; `.mdoc` bodies use the same Markdown reader for links);
  - Markdoc tag attributes and MDX JSX attributes whose string value is an old URL (the tag scanners' spans, `editMarkdocTag` / `editJsxTag`);
  - frontmatter fields with `widget: 'url'`, through `writeEntryFile`.
  - Old URLs match with or without `base`, a trailing slash, `?query` or `#hash`. The replacement keeps the original's shape.
  - Moved files keep pointing at the same files: relative links, images and `{% partial file %}` paths to anything outside the moved folder are recomputed from the new location.
- `pages.ts`: `PageService`, beside `ContentService` (which gains `locateEntries`):
  - `pages()` lists every entry in a collection with a URL (`collection`, `id`, `title`, `url`), for the link picker and duplicate checks;
  - `tree(collection)`;
  - `planMove({ collection, id, parent, slug })` validates and returns the whole change set with a summary (pages, links, redirects);
  - `move` commits that plan with expected versions;
  - `reorder` writes the parent's `_order.yaml`;
  - `createSection(folder)` creates the missing section page;
  - `redirects()` / `saveRedirects()` read the file, and write it after cleanup.
- `ContentService` changes: creating an entry under a parent (a leaf parent becomes `parent/index.md` in the same change set, at the same URL), and deleting a page also removes its `_order.yaml` line.

**Validation before a move, create or rename**, each refused in words before anything is written:
- a valid slug;
- not onto its own subtree;
- no duplicate URL in any collection;
- no static route from `src/pages`, e.g. "/contact/ is already a page on this site that isn't edited here (src/pages/contact.astro). Choose a different address.";

- `maxDepth`;
- not a page whose frontmatter sets its own `slug` (its ID doesn't follow its file).

## Phase 2.5: Markdoc tags and MDX components (design)

Scope is spec §6.5.1, §6.5.2 and the §11 Phase 2.5 entry. §13.6 is decided: an MDX component is editable only when `vesper.config.ts` declares it with a Zod props schema. Rendering real components inside the editor is v2 and stays out.

**What was found first** (measured on the playground and the jazzy-astro5 corpus):
- Markdoc nodes record line ranges only, never character offsets. Inline tags, variables and annotations have to be located in the text by Vesper's own scanner, and each scan is checked against Markdoc's tree.
- Astro parses Markdoc with its own tokenizer options: `allowComments` always, plus `html` and `allowIndentation` when the integration has `allowHTML` (or `allowIndentation` alone with `ignoreIndentation`). Phase 2 parsed with Markdoc's defaults, so in jazzy the four `{% comment %}` tags inside `<!-- -->` looked like real (undefined) tags, and the playground's inline HTML looked like text. The options live only in the integration's closure, so they are read by loading `astro.config` with `@astrojs/markdoc` wrapped to record them.
- Astro's build fails on any Markdoc error at `error` or `critical` level, except `variable-undefined` and "Partial … not found" (it resolves partial files itself and fails when one is missing).
- Markdoc strings are double-quoted, with only `\"`, `\\`, `\n`, `\r` and `\t` as escapes.
- mdast records positions for MDX JSX elements and for each attribute.
- jazzy uses `affiliateLink` 69 times, almost always inline inside paragraphs and list items, and `faq` with multi-line array attributes. Inline tags matter as much as block tags.

**Module layout.**
- `packages/core/src/body/` (the Phase 2 `files/body.ts` moves here):
  - `blocks.ts`: `parseBody` and `assembleBody`. Blocks can now be containers (a tag or component with content): an opening, child blocks, a closing. A container item keeps or replaces its opening and assembles its children with the same spacing rules as the body, recursively.
  - `markdoc.ts`: parsing with Astro's tokenizer options, top-level and nested tag structure, inline chips.
  - `markdoc-tag.ts`: a scanner for one tag's text (`{% name key=value … %}`) that records each attribute's span; Markdoc value serialization; editing an opening tag in place; new tags in house style.
  - `mdx.ts`: JSX flow elements as containers, inline JSX and expressions as chips, attribute editing from mdast's positions, a JS-literal reader for `{…}` values.
  - `inline.ts`: chips inside a Markdown block (offsets relative to the block), shared by both syntaxes.
  - `validate.ts`: Markdoc validation with Astro's filter, mapped to plain-language messages and lines; MDX props validation through an injected function.
- `packages/core/src/markdoc/`: the manifest's `markdoc` section (types), `extractMarkdocSchema(config)` (structural: reads constructors and classes by name, never imports Astro), `markdocConfigFromManifest()` for validating in the browser, and tag attributes as `FieldModel`s for the settings form.
- `packages/core/src/manifest/`: optional `markdoc` and `mdx` sections. `mdx.components[]` carries field models from `walkSchema(props)`.
- `packages/core/src/studio/`: `ContentService.listPartials()`, and body validation on save (`BodyValidator`, injected like `Validator`), returning `bodyIssues`.
- `packages/astro/src/node/load-site.ts`: loads `markdoc.config.*` (Astro's four names) through the isolated server, merges it the way Astro does (`setupConfig` from `@astrojs/markdoc/runtime`), and reads the integration's options from `astro.config`. `vesper.config.ts` gains checked `markdoc.tags` hints and `mdx.components`.
- `packages/astro/src/integration/`: the dev API validates bodies on save with the site's real Markdoc config and real Zod props schemas, and serves `GET partials`. `virtual:vesper/widgets` also exports the declared components' props schemas, so the studio validates MDX props with the real Zod schema in every mode.
- `packages/admin/src/body/`:
  - `nodes.ts`: Tiptap node types made from the manifest: one container type per tag or component with content (its content expression comes from Markdoc's `children`, so only allowed node types fit), one block card type for tags without content, one inline chip type, and the existing source block.
  - `document.ts`: builds the editor document from the nested blocks and writes it back as nested items. Inline chips become private-use placeholders (`U+E000`, hex of the source, `U+E001`) for the Markdown parser and serializer, so marks can span chips and nothing escapes them.
  - `views.tsx`: the frame, card and chip node views, each a labelled group with a Settings button.
  - `settings.tsx`: the settings dialog, built from field models and rendered with the frontmatter widgets (`Field` gets an id prefix so ids can't collide with the entry's own fields). It also has Move up, Move down and Remove, so one dialog reaches every action.
  - `insert.tsx`: the toolbar's Insert menu and the "/" plugin and listbox.
  - `issues.ts`: per-block validation for inline errors.

**How each construct appears** (the §6.5.1 table, made concrete):

| Construct | Writing view | Saved as |
|---|---|---|
| Declared tag with content, opening and closing on their own lines (callout) | Frame: "Callout · Tip", Settings, "…" menu; content editable, limited to its `children` | Opening re-written only if attributes changed; children spliced block by block; closing kept |
| Tag without content, or content on the opening's line (youtube) | Card with a one-line summary | The tag's text, attributes spliced |
| Inline tag (abbr, jazzy's affiliateLink) | Chip inside the paragraph; its text content (if plain) is a field in Settings | The paragraph is re-serialized only if it changed; each chip writes its own source |
| `{% partial file /%}` | Card with a file picker (`.mdoc` files whose name starts with `_` or that sit in a `partials` folder), stored relative to the entry | As a card |
| `{% if %}` | Frame "Shown when …", condition edited as raw text; content editable | As a container |
| `{% else /%}`, variables, functions, annotations, `{% table %}`, unknown tags, undeclared components, expressions, imports | Protected chips, block or inline, each editable as raw text in a small dialog | Byte-identical unless that chip's text is edited |
| Declared MDX component | Frame (with `children: true`) or card; props from the Zod schema; spreads and non-literal expressions kept verbatim and shown read-only | Attributes spliced from mdast positions |

**House style for new tags:** attributes in schema order, defaults and empty values omitted. Markdoc: `{% name a="x" /%}`, or `{% name a="x" %}` / content / `{% /name %}` on separate lines. MDX: `<Name a="x" />` or an opening and closing on their own lines. JSX strings use `"…"`, then `'…'`, then `{"…"}` when the value contains both quotes; other values are `{…}`.

**Editing an existing tag:** a changed attribute replaces its value's span; an attribute set back to its default or cleared is removed with its leading space; a new attribute is inserted after the nearest earlier attribute in schema order (or before the first later one). Everything else in the tag, including quoting, spacing, attribute order and multi-line values, stays byte-identical.

**Keyboard** (spec §6.5.1 accessibility):

- Escape inside a frame selects the frame; Escape on a selected block moves to the toolbar (Phase 2's way out).
- On a selected tag: Enter opens Settings, Alt+↑/↓ move it, Delete removes it. Settings has the same actions as buttons.
- Tab from inside a frame reaches that frame's Settings button only (the others are `tabIndex=-1`), so 69 chips never become 69 Tab stops.

- A new tag with attributes opens its Settings straight away.

**Validation:**
- In the browser: `Markdoc.validate()` with a config rebuilt from the manifest (types, `matches`, `required`, `children`, `selfClosing`, `inline`, partial names), on the whole body (debounced, for the summary and the save gate) and on each block's own text (for its inline message). - Blocking, as Astro's build does: Markdoc `error` and `critical`, except `variable-undefined` (Astro ignores it), Markdoc's own partial check (replaced by a check that the file exists relative to the entry), and `tag-undefined` / `function-undefined`, which are warnings because the studio may know less of the config than the build does (spec: "unknown tags: … a validation warning"). Zod props issues block.
- Messages are plain language and name the block: "YouTube video: add a title. It's required."

**Dependencies:** none new. Markdoc, mdast, Tiptap and React Aria are already in. The "/" menu is a small ProseMirror plugin, not `@tiptap/suggestion`.

## Phase 1: Core (design)

**Module layout.**
- `packages/core/src`:
  - `schema/`: the Zod 4 walker (structural, no zod import).
  - `widgets/`: inference and resolution.
  - `manifest/`: types, a pure builder, and a SHA-256 hash via Web Crypto.
  - `collections/`: glob matching and Astro-identical IDs.
  - `files/`: text codec, frontmatter split, value diff to patches, YAML read/locate/edit, JSON edit, write verification.
  - `storage/`: the interface, git blob SHA, a memory adapter, and a contract suite that takes the test framework as a parameter.
- `packages/astro/src`:
  - `fields/`: the nine helpers, importing only `astro/zod`. `fields.image` waits for Phase 2.7.
  - `config/`: `defineConfig`, which accepts the documented keys including addendum ones such as `schedule` and `search`, and warns on unknown keys.
  - `node/`: config loading, introspection, manifest writing and the local fs adapter.
  - `cli.ts`: `vesper manifest`.

**Loading the site's configs.**
- Use the site's own Vite, in an isolated `createServer`, and import through `environments.ssr.runner.import()`.
- A pre-enforced shim plugin handles the Astro modules:
  - `astro:content` re-exports Astro's real `defineCollection` and `createReference` from `astro/content/runtime`, plus `z`. Runtime-only functions throw.
  - `astro/loaders` is wrapped so the real `glob()` and `file()` still run, with their options attached under a symbol.
  - Any other `astro:*` module makes the collection read-only with a plain message.
- Function schemas are called with a marked `image`.
- A contract test per Astro major checks that the shim's exports are a superset of `templates/content/module.mjs`. It runs against Astro 7 at the root and against `fixtures/astro6-site`.
- The same loader later reads `vesper.config.ts`, `markdoc.config.mjs` and `forms.config.ts`.
- Validation always uses the user's real Zod objects.

**The walker.**
- Peel `optional`, `nullable`, `default`, `prefault`, `catch`, `readonly` and `lazy`, merging `.meta()` from inner to outer so the outermost layer wins.
- Detect image by its marker. Detect `reference` with a behavioural probe (`safeParse('x')` returns `{id, collection}`), which works on Astro 6 and 7 even though their union shapes differ.
- Map types per the §6.2 table and extract constraints.
- Refinements keep their base kind (in Zod 4 they are checks). Transforms, unions, records and tuples become `unknown`, shown as raw YAML.
- It never throws: each field is wrapped in try/catch and failures become diagnostics.

**Widget resolution.**
- Runs at manifest build, in Node, where the `match` and `accepts` functions from `vesper.config.ts` can be called.
- The manifest stores both the resolved and the inferred widget, plus warnings. The browser only looks components up by name.

**Manifest.**
- Versioned and deterministic: POSIX paths, no timestamps.
- Includes collections (source, editable or read-only with a reason, fields, presentation), forms, and diagnostics.
- Phase 1 emits it from the CLI. Phase 2 adds `astro sync` and `dist/_vesper/manifest.json`.

**Serializers.**
- Split frontmatter with Astro's exact regex, keeping BOM and EOL.
- Read values with js-yaml.
- Locate nodes with `yaml` (`keepSourceTokens`), but only when it parses with no errors and its values deep-equal js-yaml's. Otherwise the block is source-only.
- **Splice minimal edits into the original text:**
  - scalars keep their style;
  - dates keep their shape and offset;
  - added and deleted keys are line-based;
  - each line keeps its own line ending.
- The Document API is a flagged fallback, used only for anchors, aliases and tags.
- Every write is re-read and deep-compared before it is stored.
- JSON is edited with `jsonc-parser` `modify`/`applyEdits`.
- `file()` entries are located by id at write time.
- A no-op save returns the original bytes. TOML is read-only in v1.

**Storage adapter.**
- Methods: `head`, `list`, `read`, and `commit(ChangeSet)`, where a ChangeSet holds `put`, `delete` and `move` changes with `expectedVersion`.
- `version` is the git blob SHA-1, so memory, local, GitHub and cloud adapters all agree, and Phase 4's `base_sha` works unchanged.

**Dependencies, each with its reason:**
- `js-yaml`: Astro's own parser.
- `yaml`: the lossless CST.
- `jsonc-parser`: formatting-preserving JSON edits.
- `github-slugger`: ID parity with Astro.
- `picomatch`: the matcher Astro uses.

**Tests mapped to the "Done when" criteria:**
- **Manifest snapshots** for every playground collection and the Astro 6 fixture, cross-checked against `.astro/data-store.json`.
- **Corpus:** `sources.json` records repo, commit and path for files from Jeremy's three own sites, about 120 in total (well over 30), plus synthetic gaps: JSON indents, anchors, BOM, TOML, MDX imports, CRLF and mixed EOL. `VESPER_PRIVATE_CORPUS` adds the client sites, locally only.
- **"No unrelated diff"** has two parts:
  - a no-op save is byte-identical;
  - editing path P changes only P's byte range, keeps untouched lines' EOLs, and re-reads to the expected value.
- **Raw-field fallbacks:** a table of unmappable schema types, each expected to fall back.
- **Meta placement:** every wrapper order and every meta position produces the same field model.
- **Widgets:** an unknown widget, or one whose `accepts` rejects the field, falls back with a warning that names the field and the widget.

## Risks and early spikes
- **S0:** the source-condition dev loop on Windows (Phase 0). Fallback: tsc watch.
- **Astro internals drift.** Mitigation: use only public exports, plus a shim contract test per major.
- **The `@vesper` npm scope may be taken (§13.1).** Packages stay private and unpublished through Phase 1, so a rename then is cheap. On 2026-10-19 no package was published under `@vesper`; Jeremy claims the org.
- **Sample-file licensing.** Only CC0, public-domain or MIT-compatible files, with provenance recorded in the README.
