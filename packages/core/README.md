# @vesper/core

The framework-free heart of Vesper. It runs unchanged in Node, in Cloudflare Workers and in the browser, so it imports nothing from Node, Astro, React, Vite or Zod.

**Status:** Phases 1 to 3 complete; Phase 4's shared pieces (the cloud) built.

| Area | Exports |
|---|---|
| **Files** (spec §6.5) | `readEntryFile` / `writeEntryFile` for `.md`, `.mdx` and `.mdoc`. `readDataFile` / `writeDataFile` and `readCollectionFile` / `writeCollectionEntry` for JSON and YAML data. Lower-level `readYaml` / `writeYaml`, `readJson` / `writeJson`, `splitFrontmatter` and `diffValues`. |
| **Bodies** (spec §6.5, §6.5.1, §6.5.2) | `parseBody` splits a body into blocks with exact ranges: Markdown, protected source, and tags (Markdoc tags and MDX elements, as containers with child blocks when laid out on their own lines). Inline tags, variables, annotations and inline JSX are chips. Markdoc is parsed with Astro's tokenizer options (`parseMarkdoc`). `assembleBody` splices edited items back, keeping untouched bytes, containers' openings and closings included. |
| **Tags** | `markdocTags` / `markdocTagLayout` / `editMarkdocTag` and `jsxTagLayout` / `editJsxTag` read a tag's attributes with their spans and change one attribute's bytes in place. `markdocOpening` / `jsxOpening` write new tags in house style. |
| **Body validation** | `validateMarkdocBody` blocks exactly what Astro's build fails on, in plain language; `validateMdxBody` checks declared components with an injected props check. `resolvePartial` / `partialChecker` find partial files as Astro does. |
| **Schema** (spec §6.2, §6.3) | `walkSchema` turns Zod 4 schemas into `FieldModel`s without importing Zod. `resolveWidgets` applies the spec §6.3 order. |
| **Manifest** | `buildManifest`, deterministic and hashed. Its optional `markdoc` section (from `extractMarkdocSchema`, structural, never importing Markdoc's config code) and `mdx` section carry tags, attributes, settings fields and declared components. `markdocConfigFromManifest` rebuilds a config `Markdoc.validate()` accepts in the browser. |
| **Collections** | `globMatcher` and `defaultEntryId`, identical to Astro's glob loader. `folderKey` slugs a folder path the same way. |
| **URLs** (spec §6.15, also `@vesper/core/urls`) | `entryUrlKey` expands a collection's `url` pattern (`:id`, `:path`, `:slug`, `:<field>`, `:<date>\|yyyy`) or runs its function form; `formatUrl` adds Astro's `base` and trailing slash; `urlKey` / `parseSiteUrl` read a link back. `buildTree`, `childrenOf` and `breadcrumbsOf` nest a tree collection by folder and order it by `_order.yaml`. `cleanRedirects` collapses chains, removes loops and drops redirects onto real pages; `hostRedirects` and the rule writers produce `_redirects`, `.htaccess`, nginx and Vercel rules; `parseRedirectsCsv` reads plain, WordPress and Drupal exports. `@vesper/core/urls` is the same without the parsers, for a site's own pages. |
| **Images** (spec §6.6, also `@vesper/core/images`) | `siteRatios` (the site's ratios plus the built-in `og`) and `ratioLabel` ("16:9"). `cropForRatio` gives a ratio's crop: the stored one, fitted to its ratio, or the largest rectangle centred on the focal point (`focalCrop`). `pixelRect` rounds a crop to pixels; `moveRect`, `resizeRect` and `dragCorner` are the crop dialog's moves; `focusWithin` and `objectPosition` place the focal point in CSS; `sharpAnchor` is where Astro's own server crop lands. Shared by the studio, `<Img>` and the crop step, so all three cut the same rectangle. |
| **Accessibility** (spec §6.18) | Layer 1, the studio's checks, as plain functions so every storage mode and the cloud share them. `entryChecker(manifest)` checks an entry's fields (`checkFields`: image alt text, `fields.color({ contrast })` against the site's `a11y.backgrounds`, compact Markdown, PDFs in file fields) and its body (`checkBody`: alt text, heading order and empty headings from the collection's `headingStart`, vague and new-tab links, tables without a header row, typed lists, empty names on embeds, video captions, linked PDFs). Every note is an `A11yNote`: one of the seventeen rules in `A11Y_RULES`, a plain message, why it matters, and its field path or body offsets and line. `pdfNotes` turns what the studio read from a PDF into notes; `blockingNotes` is the publish gate. `BUILD_RULES` are the axe-core structure rules the build runs (layer 2), in the same message style. `contrastRatio` is WCAG 2.1's. Vesper reports problems; it never claims compliance (D19). |
| **Studio services** | `ContentService` lists, reads, creates, saves and deletes entries over any storage adapter. `MediaService` lists and uploads media. `PageService` serves a tree's outline, moves a page and everything under it as one change set (its files, both `_order.yaml` files, a redirect per page, every rewritten link), reorders, creates section pages and edits the redirects file; `pageEntries` gives every entry's URL key and file, for tracing built pages to entries. `rewriteBody` / `rewriteValues` change links to moved pages and keep relative paths pointing at the same files. |
| **Storage** | The `StorageAdapter` interface, `MemoryStorage`, `gitBlobSha`, and the contract suite at `@vesper/core/testing`. `GitHubStorage` is GitHub mode's (spec §6.8), with `fetch` alone, so it runs in the browser and in Workers: the branch as one snapshot (its commit and recursive tree), bytes by blob SHA through an optional `BlobCache` and GraphQL batches, each checked against its SHA, and one commit per save through the Git Data API, built again once on another's push that touched other files. A deferred change set (`defer`) holds new files for the next commit, so an entry and its upload are one commit. `GitHubError` says what went wrong in plain words. |
| **The cloud** (spec §6.9, §7) | What the studio and the cloud must agree on, so both run the same code. **Grants** (§7.5): `fileAccess`, `changeAccess` and `wholeSite` evaluate a member's role and grants, matched on file paths (`grantKey`, `grantMatches`), never entry IDs; a move needs both ends, new media an edit right, the redirects file the whole site. **DPoP** (RFC 9449): `createDpopKey` (non-extractable), `createDpopProof`, `verifyDpopProof`, `jwkThumbprint`, on WebCrypto. **Drafts** (§7.4): `saveDraft` keeps the bytes a save would write, checked by `validateChangeSet` against the site as its drafts show it, joining drafts a save touches; `overlayEntries` / `readOverlay` show the site with them; `publishChangeSet` makes the one commit that publishes some, expecting each file's base version; `rebaseDraft`, `discardDraft`. **The API**: its request and response types, `encodeChange` / `decodeChange`, and `CloudClient` (PKCE with `createPkce` and `authorizeUrl`, a DPoP proof on every request, the access token renewed with the rotating refresh token). Scheduled publishing (§6.17): `GET /schedule` says the site's trigger, whether it holds scheduled drafts and where each change stands; `POST /schedule` holds drafts until a time (`hold`), and `DELETE /schedule/{id}` releases them. `runCloudContract` at `@vesper/core/cloud-testing` is what the studio relies on from the cloud: the fake cloud and the real one both run it. |
| **Field checks** | `fieldModelIssues` checks values from the field model alone (required, choices, numbers, patterns): GitHub mode's stand-in when the site's schemas can't load in the browser. |

Saves change only the bytes of values that changed: an unchanged save returns identical bytes. Every write is re-read and verified before it is returned. When a save can't be done exactly, it throws `SerializationError` and nothing is written.

See `test/README.md` for the round-trip corpus, and DECISIONS.md for the reasons behind each choice.

## Development

From the repository root:

```bash
npm test            # Vitest, straight from src/
npm run typecheck   # tsc -b plus the test tsconfig
npm run check:dist  # builds dist/ and imports it the way npm consumers will
```

Inside this workspace, `@vesper/core` resolves to `src/index.ts` through the `@vesper/source` export condition. Published consumers get `dist/`.
